# Mesa glossary

Shared vocabulary for issues, code, receipts, and screens. Use these terms as written. Each entry names the synonyms to avoid so the same thing is never called two names.

## Profile

A named configuration under `~/.mesa/<name>/`: `config.yaml` (`vault` path, `defaultAgent`, enabled `skills`, `decisions.backend` (`rules`, the only one since ADR-0020; an older file that says `adapter`, or still has `decisions.adapter`, loads and acts as `rules`) and `decisions.threshold` (the confidence below which the rules would defer to the backend the profile names, ADR-0003), `sessions.log` (whether each session's window writes its Output log, on by default), `sessions.statusLineCost` (whether Claude's status line in Mesa sessions ends with the session's estimated cost, off by default), `terminal.app` (the app `mesa attach --app` opens: `Terminal` by default, `iTerm`, `Ghostty`, or `WezTerm`), `shortcuts` (the app's Search Mesa, Board and New session keys, listed and edited in Shortcuts; Mod is Command on macOS, and duplicate or reserved keys are refused), `run.permissionMode` and `run.allowedTools` (how a Skill run's claude may act: its `--permission-mode`, `acceptEdits` by default, one of the six claude takes, and the `--allowedTools` rules it gets, such as `Bash(git log:*)`, none by default, which leaves the mode's own), `agents` (each agent's native launch defaults on new and resumed sessions, in its own terms and never translated: `agents.claude.skipPermissions` (`--dangerously-skip-permissions`), `agents.codex.approvalPolicy` (`--ask-for-approval`, `on-request` or `never`), `agents.codex.sandbox` (`--sandbox`, `read-only`, `workspace-write`, or `danger-full-access`; a Codex session with `--with` gets `workspace-write` when it is unset or `read-only`, for read-only with a warning and a kept receipt, see Additional project) and `agents.codex.bypass` (`--dangerously-bypass-approvals-and-sandbox`, which then replaces the other two), and `agents.antigravity.skipPermissions`, `agents.antigravity.mode` (`--mode`, `accept-edits` or `plan`) and `agents.antigravity.sandbox`; each unset by default, which passes nothing and leaves the agent's native config, and a session's Plan mode wins over a configured mode, Claude's skip permissions included; Settings > Coding Agents edits them, the dangerous ones in red), and `keys` (literals or `env:VAR` references, always printed as `***`)), `registry.yaml`, and `sessions/`. `mesa init` creates it and lays out its vault (as `mesa vault init` does, when Mesa may write into that folder); `mesa config` reads and edits it. Exactly one vault per profile. `default` is created on first run; `mesa --profile work` or `MESA_PROFILE=work` selects another. Work and personal are two profiles, never one shared vault.
Not: workspace, account, environment.

## Vault

The Obsidian vault a profile owns. Layout: `raw/` (immutable inputs), `wiki/` (agent-written knowledge), `projects/`, `receipts/`, `daily/`, `AGENTS.md` (the vault's own schema), `index.md`, and an append-only `log.md`. Mesa writes files; Obsidian renders them. `mesa vault init` lays the layout out (only what is missing; a folder that is neither empty nor a vault needs `--force`), and `mesa vault status` lists what is missing. The `AGENTS.md` it writes holds the note conventions the `mesa-vault` skill teaches and the Receipt policy; a vault's existing `AGENTS.md` is never rewritten. Receipts and Session writes go through `writeNote`: atomically (a temp file, flushed, then a rename), with `created`, `updated` (local `YYYY-MM-DDTHH:mm`, the form Obsidian infers as Date & Time), and `source: mesa` in the frontmatter, and never over a note whose frontmatter says `locked: true`. Read-modify-write updates of shared notes run under the vault lock, `.mesa/lock` in the vault. `mesa log` appends one explicit line to `log.md` (append-only) and rebuilds today's Daily note under the same lock. `mesa vault open [note]` opens the vault, or one item (the exact path, else the note `<path>.md`), in Obsidian through its `obsidian://open` URI (`--cli` uses the Obsidian CLI when it is registered); Obsidian must already know the vault ("Open folder as vault" once). Vault content never enters this repo.
Not: notes folder, knowledge base, memory (memory is what the vault holds, not the vault).

## Map

`mesa map [--all] --json` regenerates `map.canvas` in the active profile's laid-out vault from saved session records, never a live provider scan. The default inclusive window is the last 30 elapsed days through the injected clock's current instant, plus transitive resume ancestors present in that profile; `--all` includes every saved record. Included projects have groups, with registered labels, General's reserved identity, and slug labels for orphan records. Hidden projects and ended/archived/terminal/run records remain eligible. Stable string IDs and fixed geometry keep unchanged bytes and mtime, without receipts or log/index changes. Update replaces personal edits, warned in the first text node. Exact available summaries become file nodes; other nodes show recorded state and a clipped goal, with profile-qualified `mesa://session/<id>?profile=<profile>` links. The app waits for active-profile information at startup, looks up a session only in that profile, and quietly explains mismatches, unknown ids and malformed links without switching profiles or cloning. Bare session links look up only the active profile; clone links keep their existing confirmed checkout flow. The shared scoped Canvas preview keeps its counts/texts and exposes validated geometry; malformed geometry is unavailable to the Map screen. Map draws every saved group, node and directed edge at its saved coordinates, with fit/scroll and keyboard-accessible target buttons. A file node opens its exact vault file, with a separate session action; a text session node opens the session. Map reads its saved file and offers explicit Update and Open in Obsidian; drawing never rewrites it.

## Daily

The local calendar day's meaningful history at `daily/YYYY-MM-DD.md`: `mesa daily [--date YYYY-MM-DD] --json` returns `{path, date, changed, decisions, changes, log}`. Daily (`daily/service.ts`) reads all receipts, deduplicates ids, buckets `started` by local day (both local timestamps and legacy UTC), and uses the Receipt policy for decisions, substantive vault changes and material guardrails. Daily-target bookkeeping, routine history and raw terminal tails are excluded. Receipt lines have time/summary, an exact receipt link, and an exact target link only when its string path is in Vault scope; missing or invalid targets never discard a meaningful entry.

Only the bytes between one ordered pair of `<!-- mesa:daily:start -->` / `<!-- mesa:daily:end -->` are replaced. Existing frontmatter, newline forms and all outside bytes are preserved, never serialized through writeNote. No markers appends the generated section; partial, duplicate or reversed markers refuse. New notes have the daily conventions and stamped frontmatter. Unchanged builds make no write, receipt or log entry. The app's Daily view defaults to local today, reads/refreshes through the Vault reader, follows exact links into Vault, and has explicit Rebuild and Open in Obsidian; reading never rebuilds.

`mesa log` adds `<!-- mesa:log -->` after the existing normalized user text to identify a new explicit event. Unmarked legacy lines are excluded only for the exact vault-init text or the full automatic receipt summary/link produced by the receipt owner; other user wikilinks remain explicit. An old user line identical to that automatic format is indistinguishable and is excluded. No legacy line is rewritten. An exact legacy log line already outside the generated section remains there and is not duplicated inside it.

Standalone rebuilding and explicit logging use one Daily lock owner and a private unlocked rebuild. Both destinations' scope, frontmatter and lock state, plus the Daily markers, are checked before append. The two files cannot be replaced atomically together: if log.md persists and a later rebuild fails, the error names the persisted write and instructs `mesa daily`, without logging again, to recover. Unrelated notes and user sections remain the person's.

## Vault scope

Which vault paths Mesa may read or write: a vault-relative path that is not empty or absolute, has no `..` part, names no vault internal, and whose real target, through any symlinked file or folder on the way, stays in the vault and is not an internal. The internals are `.obsidian/`, `.mesa/`, `.trash/`, `.git/`, and `.DS_Store`, in any folder and any case: application state, never knowledge. The target is followed to the nearest part that exists, so a note not written yet is in scope, and a link whose target is missing is not. `vault/scope.ts` is the one owner: `outOfScope` says why a path is out (`outside the vault`, `a vault internal`, or `a broken link`), and `vaultFile` resolves a path in scope or refuses it as a usage error with that reason. `vaultWriteFile` additionally checks the written and canonical project folders against a note's project, including symlinked ancestors of files not written yet; General cannot write into a project folder. `log.md` uses the same path gate before any session save. Every note read and write, `mesa vault open`, the inventory, the reader, the search, and the Vault server's tools go through it.
Not: sandbox, allowed projects (a session's project scope is a later, narrower rule over this one).

## Vault inventory

Every item in the active profile's vault but its internals, with no cap: `listVault` (`vault/inventory.ts`). Each item is `{path, kind, category, project?, size, modified, unavailable?}`. `kind` is `markdown` (.md), `canvas`, `base`, `attachment` (Obsidian's image, audio, video, and PDF formats, by extension) or `other`. `category` is the top folder (`raw`, `wiki`, `projects`, `receipts`, `daily`), `index`, `log`, `agents` (the top-level `AGENTS.md`), or `user` for any other folder or top-level file. `project` is the frontmatter's `project:`, else `<name>` for `projects/<name>.md` and anything under `projects/<name>/`: the one membership rule (`itemProject`, `vault/item.ts`). Only a markdown file in scope is read, for its frontmatter. A symlink out of scope is listed with its reason as `unavailable` and never read or followed; a link to a folder in the vault is listed as `a folder link` and not walked, since its items are listed where they are; a folder that does not open is one `unreadable` item. `mesa vault list [--project <p>] [--type <kind or category>]` prints `{vault, total, items}` sorted by path; an unknown type is a usage error, a missing vault folder `not_found`, and a vault path that is a file `invalid_config`. `modified` is the file's modification time here and in `mesa vault read`, so the CLI and the app agree on what is current. The app's Vault screen (the sidebar's Vault) shows the inventory as a folder tree with counts, only its top level open at first, filtered by project and type with the same rule (`matchesVaultFilter`), and the selected item's path, kind, category, project, size, and modified time, with the item itself below (Vault reader). Receipts are one folder here, not a feed. The screen looks at the vault again every five seconds and whenever the window gains focus, one look at a time (`useVaultLook`), and refreshes the open item and current search with each look, so notes changed outside Mesa show with the selection and scroll kept; a selected item the list no longer has says "This item no longer exists". A missing vault folder, one that does not open, an empty vault, and one not laid out (`mesa vault status`) each say so in the screen with the fix, `mesa vault init` or `mesa config set vault <path>`, never in a toast. What it shows belongs to the profile whose bridge listed it (an app window runs one, by `MESA_PROFILE`) and to the vault that list named: another profile or a moved vault clears the list, selection, reader, and search at once, and a reply for the one before never shows.
Not: search, reader, Receipts page.

## Vault reader

One vault item as Mesa shows it: `readVaultItem` (`vault/reader.ts`) and `mesa vault read <path>` (`--json` prints it). It is the inventory's item plus `uri` (its exact `obsidian://open`), `backlinks` (every other Markdown item with a link that resolves to it, by path; each read scans every Markdown item), and a `preview`: `markdown` with `frontmatter`, `body`, and `links`; `canvas` with its `nodes` and `edges` counts and its text nodes' `texts`; `base` with its `yaml`; or `unsupported` with a `reason`, for an attachment, any other file, a canvas that is not JSON Canvas, and a file the system does not let Mesa open. A note whose frontmatter does not parse is all body. A path out of the vault's scope, or one the inventory lists as unavailable, is a usage error, except an unreadable Markdown file keeps its `unsupported` preview and system-read reason; one it does not list is `not_found`. Links have one owner, `vault/links.ts`: wikilinks `[[target#subpath|alias]]`, embeds `![[...]]` and `![...](...)`, and Markdown links `[text](path)` (decoded; a URL is not a link), none inside fenced, indented, or inline code, each with its offsets in the body. Each resolves as Obsidian resolves it, to `resolved` with its `path`, `broken`, or `ambiguous` with its `candidates` (never guessed): a Markdown link, or a target starting `./` or `../`, is first a path from the note's folder; then the exact vault path; else every item whose file name is the target's, or whose path ends with a path-qualified target, case aside. `.md` may be left out; any other extension (an attachment's, a canvas's) is named. No target (`[[#Heading]]`) is the note itself. The Vault screen shows a note's properties as a table, its Markdown with resolved links that select their item (the tree opens to it), broken and ambiguous links marked and listed with why and the candidates to pick, and its Backlinks; every other kind says "Preview not available" with what Mesa shows of it and Open in Obsidian.
Not: editor, search, preview (one field of a read).

## Vault search

Finding vault items by their words: `searchVault` (`vault/search.ts`), `mesa vault search <words...> [--project <p>] [--type <kind or category>] [--limit <n>]`, and the Vault screen's search box. An item matches when every word is in it, case aside: in its path, a note's frontmatter values (not its keys) or body, a canvas's text nodes, or a base's YAML; an attachment or any other file is matched by its path alone. It searches the inventory's items with the inventory's project and type rule (`matchesVaultFilter`), skips every item the inventory lists as unavailable, so internals and links out of scope never appear, and reads each through `vaultFile`. Each result is `{path, kind, project?, title, matches}`: `title` is the file name (without `.md` for a note, as Obsidian titles it), and `matches` at most 3 `{line, text}` snippets of at most 200 characters, a long line cut to the part around the word; a note's line numbers are its file's, and a canvas's count its text nodes' lines in order. Items whose path holds every word come first, then the newest. `--limit` (50 by default) caps `items`, and `--json` prints `{total, truncated, items}`. No word, or a limit that is not a positive whole number, is a usage error. Each search reads every Markdown, canvas, and base item: there is no index. The Vault screen's search box (Enter searches) shows the results in the tree's place under its project and type filters, each with its snippets; one selects its item in the reader, no result says so, and an emptied box gives the tree back. Search Mesa offers Search vault, last, for any typed text; it opens the Vault screen searching that text. `mesa search` lists it too.
Not: index, fuzzy search, Search Mesa (the palette over Mesa's destinations).

## Vault browser

The app's Vault screen, the sidebar's Vault: the whole active-profile vault as the Vault inventory's folder tree and filters, the selected item through the Vault reader, and Vault search's box, over the same owners and Vault scope as the Vault server's tools. It opens any item in Obsidian. Write Bases views calls Vault Bases; it does not edit notes.
Not: Receipts page, file manager, editor.

## Vault health

A read-only snapshot of navigation and project-discovery findings: `vaultHealth` (`vault/health.ts`), `mesa vault health --json`, and the Vault screen's Check health action. The result is `{vault, checked, findings, limitations}`. Each finding names its `kind`, vault-relative `path`, a file `line` when tied to text, and a `message`; link findings include their `target` and ambiguous candidates. It checks Markdown knowledge notes and `index.md` through the existing Vault inventory, scope and link resolver. Broken file targets, ambiguous targets, stale index links, invalid frontmatter, wiki notes without a project association, and unavailable items are reported. A note with no incoming link from another knowledge note or the index is an orphan; self-links do not count, and project hubs are entry points exempt from that finding. Orphans and unassigned shared notes may be intentional. Raw inputs, receipts, daily notes and layout instructions are excluded from knowledge-quality checks. Heading/block fragments, Canvas/Bases contents, semantic contradictions and factual freshness are not checked. Checking changes no file, mtime, receipt, log or cache, and never repairs a finding. Results describe the last explicit check; the app opens a finding's exact path and clears results on a profile change.
Not: repair, semantic audit, index rebuild, background task.

## Vault Bases

`mesa vault bases --json` and the Vault screen's Write Bases views call `vault/bases.ts`: derived raw YAML at the two fixed scoped paths `receipts.base` and `sessions.base`, atomically under the vault lock. The exact leading ownership comment is `# Generated by Mesa: Bases views`. Unmarked files are kept; owned identical bytes are kept without a write or mtime change. The result is `{written, kept}`, vault-relative paths, and generates no receipt or log entry. The existing Base reader exposes ordered string view names from valid YAML independently of write ownership, including arbitrary user Bases and generated files whose comment native Obsidian removes. Reading never adopts a file. The shared app reader shows those names with the raw YAML and Open in Obsidian. Malformed YAML or invalid/missing view names retain the YAML fallback.

The first receipts view, Meaningful, is a table sorted by started descending, with file, started, kind, project, session, status and target columns. By kind uses grouped cards with the same view-local filter from `receipts/policy.ts`: successful decisions and vault changes, successful guardrails with a string override or `dangerousFlags`, failed/blocked guardrails whose error is `guardrail_blocked`, excluding string targets `daily` and `daily/`. Legacy (all receipts) has no meaningful filter, so historical receipts without kind and routine history remain accessible. Global scope is Markdown in the receipts folder. A guarded nested `outputs.target` formula links the exact nonempty string when it passes lexical Vault scope (no absolute/traversal/internal path), otherwise the receipt's `file.asLink()`. Bases cannot check symlink targets; Mesa note writes already canonicalise their targets. The sessions default table selects session-summary and decision Markdown notes outside the receipts folder with file, type, project, session and updated columns, sorted updated descending; By project groups cards by project. These are compatible tables and grouped cards, not a Mesa results renderer. Native Obsidian rendering is separate from YAML and expression-fixture checks.

## Project hub

A project's note in the vault, `projects/<name>.md` (`projectHubPath`, `vault/layout.ts`), with short sections (Purpose, Status, Decisions, Links), each a few lines linking to the wiki notes that hold the detail, as the vault's `AGENTS.md` and the `mesa-vault` skill describe. `mesa run project-brief` regenerates it and keeps the blocks between paired `<!-- keep -->` markers. The Project context shows its headings and the start of its body.
Not: project page, brief (the brief is the skill run that writes it).

## Project context

A project's bounded overview, what a session reads on demand when earlier work bears on its task: `projectContext` (`vault/project-context.ts`), `mesa vault context <project> --json`, and the `project_context` tool. It is `{project, hub, index, notes, decisions, goals, more}`. `hub` is the Project hub's `path`, its `headings` as written (at most 12), and the first 2,000 characters of its body as `excerpt`, or null. `index` holds the `index.md` lines with a link that resolves to one of the project's items, in order, at most 20. `notes` are its other Markdown items (the inventory's project rule; not the hub, receipts, or the layout notes) as `{path, title, modified}`, at most 20, newest first; a title is the frontmatter's `title`, else the first `# ` heading, else the file name. `decisions` are its notes with `type: decision` as `{title, path, when}`, `when` being the day the file name starts with, else the day it changed, at most 10, newest first: the decision note is their one owner, and decision receipts stay history. `goals` are its first 10 earlier session goals. `more` says what was left out and which commands read the rest. The JSON is at most 8,000 bytes whatever the vault holds: past the caps, the longest list gives up its last entries first, then the excerpt shortens, and `more` counts what went. The same vault and sessions give the same overview. `--general` is the General project: the whole vault, no hub, `counts` of items per category, every index line with a link, and the General sessions' goals. A project with nothing yet, or a vault not laid out, gives empty lists and a `more` hint; an unregistered project is `not_found`. `mesa vault goals <project> [--general] [--limit <n>]` (`sessionGoals`, `vault/session-goals.ts`, the `session_goals` tool) lists the project's agent sessions from the session store (not plain terminals or skill runs), ended and archived ones too, newest first, 20 by default, each `{id, agent, started, ended?, goal?, summary?}`: the goal cut to 300 characters, and `summary`, its `wiki/sessions/<id>.md`, when the vault has one. Both leave out the Caller, or the session a caller names (`exclude`). The project workspace shows the overview as its Vault panel: the hub's excerpt with Open in Obsidian, related notes that open the Vault screen with that item selected, and recent goals; a project with none of them gets one quiet line.
Not: brief, summary, memory (the vault holds memory; this is a view of it).

## Vault server

`mesa vault mcp`, the `mesa-vault` MCP server a session's agent starts (the launch mount runs `<mesa> vault mcp`, with no `--profile`): newline-delimited JSON-RPC 2.0 on stdio, with no network listener (ADR-0011). It answers `initialize` (the client's protocol version when it speaks it, else `2025-11-25`), `ping`, `tools/list`, and `tools/call`. It never replies to a notification, and answers any other method, such as Antigravity's `server/discover`, with `-32601`. Only JSON-RPC goes to stdout; stderr says whom it serves. Invalid envelopes, including a version other than `2.0` or an id other than a finite number or string, receive `-32600` with id null before dispatch. Its binding (`vault/binding.ts`) is the session `MESA_SESSION_ID` names in the profile `MESA_PROFILE` selects, checked again on every request. With a session record that does not read, no `MESA_SESSION_ID`, a session the profile does not have (unknown, removed, or another profile's), or one that has ended (stopped, even while its server runs), it is inert: it completes `initialize`, lists no tools, and answers every call with the tool error `mesa-vault is inert: <reason>`, reading and writing nothing. A background Claude process keeps the binding it started with (Native background session), so once its record has ended and a Mesa resume attached to the same process, the server serves the last record resuming it. Its seven tools (`vault/tools.ts`, each one line and a strict schema) call the owner of a `mesa vault` command and answer with that command's `--json` data as text: `project_context` (`[project]`, Project context), `read_note` (`path`, Vault reader), `search_vault` (`query [project] [all] [limit]`, Vault search), `session_goals` (`[limit]`), and the Session writes `save_decision` (`title decision rationale [probabilities] [confidence]`), `save_summary` (`summary`), and `save_note` (`title body [path]`). Reads default to the session's project, the whole vault for a General session, and leave the session out of its goals; `search_vault` takes another `project`, or `all`. Writes are the session's and its project's: the session in the note and as its receipt's `actor`, a note in another project's folder refused, and no `save_decision` from a General session. A path out of the Vault scope, arguments the schema refuses, and an owner's refusal are tool errors with the reason; an unknown tool is `-32602`. Reads record nothing, and a save records as its Session write does. `mesa vault mcp --tools [--json]` prints `{tools}`, the definitions, without serving: 2,608 bytes whatever the vault holds. The app's Session details lists them as Vault tools for an agent's session; a plain terminal has none.
Not: MCP connection, vault API, plugin.

## Project

A repository registered with a profile through its `mesa.yaml`: `name` (a stable ASCII slug, at most 252 characters so `projects/<name>.md` fits a macOS filename, unique in the profile), preferred `agent`, `priority` (0 to 1, feeds the attention score), `guardrail` (`normal` or `strict`, see Guardrail), `tmux.layout` (how its Project view lays out its sessions), extra `skills`, and Project overrides. A project has zero or more sessions. Its profile-local display label can change without changing its slug or historical session links. `mesa register <path> --create --label <name>` sets that optional display name during registration; the app's Add project dialog accepts a path or folder picker and an optional Name. The sidebar's Add project menu also offers Import workspace: choose or type a folder, scan, then import individual results. `mesa projects discover <folder>` scans at most three levels, 500 folders and 100 local Git or configured project candidates for selective import through `mesa register`. `mesa projects clone <url>` accepts a validated HTTPS or SSH URL, or a `mesa://clone?url=<encoded-url>` link, clones under `~/.mesa/<profile>/checkouts/`, then registers it; a failed clone removes only its new checkout.
Not: repo (a repo becomes a project once registered), workspace.

## Project override

A profile setting a project's `mesa.yaml` sets for that project alone (ADR-0013): `worktrees.base`, `worktrees.fetch`, `worktrees.carryIgnoredDirectories`, `worktrees.sparseDirectories`, `worktrees.setup`, `worktrees.teardown`, and `terminal.theme`, each valid as the profile's would be. One left out is the profile's. Worktree creation, session launch, setup reruns, and the remove preview and its teardown use the project's value (`worktreeSettings` and `worktreeScript`, `worktrees/settings.ts`); the project's session terminals in the app use its theme. A project's own `setup` or `teardown` runs only once this profile has approved that exact argv: its sha256 is kept in the project's registry entry (`approved`, `worktrees/approval.ts`), outside the repository. Any other or changed argv is `needs_approval` (exit 10), which names it and its fingerprint, and nothing is created or removed. `mesa projects trust <project> --expect <sha256>...` approves only the scripts with those reviewed fingerprints, with a kept guardrail receipt, and refuses if `mesa.yaml` changed since; without `--expect` it shows each argv and fingerprint and asks in a terminal, refusing with the `--expect` command when no one can be asked. The app's Approve dialog passes the fingerprints of the scripts it shows; `mesa projects set` approves an argv a person writes; approval comes only from outside a Mesa session (the app or a plain terminal): with `MESA_SESSION_ID` set, `trust` is a usage error, a setup or teardown `set` writes stays unapproved, and `mesa config set` refuses to change the profile's own `worktrees.setup` or `worktrees.teardown`, by path or through `worktrees`; an empty list runs nothing and needs no approval. The profile's own `config.yaml` scripts need no approval. `mesa projects set <project> <path> <value>` writes one, the value read as YAML, and `--unset` removes it, keeping the file's other keys, order, and comments; `mesa projects --json` shows each project's `overrides`, its effective `terminalTheme`, and its `unapproved` scripts. The app edits them in Settings > Projects, which picks a project and names the profile value each row would inherit; an empty field there removes the override, a script row chooses the profile's, None (an empty list), or Custom, and unapproved scripts open an Approve dialog showing each argv.
Not: project settings, profile config (the overrides are in the project's file).

## Registry

A profile's `registry.yaml`: one entry per project, its stable name and the directory holding its `mesa.yaml`, plus optional display label, pin and hide settings. Entry order is the manual project order; pinned projects appear first in the app sidebar, hidden projects remain accessible through project search or the CLI. The desktop has no standalone Projects overview: its Projects tab shows sidebar folders while preserving the current content, and a folder opens its individual workspace. The icon beside Your projects opens sorting choices: Recent (latest workspace visit), Last session (latest persisted session start, including ended sessions), Active sessions (non-ended, non-archived records outside final states), and Most visited (workspace visit count). Pinned projects stay first and ties keep registry order. `mesa projects --sort recent|last-session|active-sessions|most-visited --json` uses the same ordering. `mesa projects visit <name> --json` atomically updates optional `visitedAt` and `visits` in the registry without writing receipts or changing mesa.yaml. Sorting selection lasts for the app run; visit history survives restart. `mesa projects` reads it; `mesa projects update <name>` changes presentation and order; `mesa register <path>` appends to it; `mesa unregister <name>` removes an entry without removing the folder or session history. Writes rewrite it whole under `registry.yaml.lock`, so concurrent changes keep both entries.
Not: project list, index.

## Agent

The CLI coding agent a session runs: `claude` (Claude Code), `codex` (Codex CLI), or `antigravity` (Antigravity CLI, executable `agy`). All run interactively in a Mesa window and can run skills headlessly. Claude Code and Codex report states through hooks (ADR-0003); Antigravity exposes only qualified TUI state markers and a private per-session log for its native conversation ID after the first prompt. Antigravity context use and adoption are not read yet; Codex adoption reads native interactive rollouts. Every agent session has the `mesa-vault` MCP server (`mesa vault mcp`, bound to the window's `MESA_SESSION_ID` and `MESA_PROFILE`) with its tools pre-approved: Claude Code and Codex through their launch argv, which every start, resume, fork, and headless run repeats; Antigravity through one global entry and allow rule that `mesa hooks install` writes (ADR-0012).
Not: model, assistant, bot.

`mesa agents --json` reports each provider's native-operation catalog alongside Doctor's current installed/version probe. The catalog names the version used for P4 qualification and marks native operations Mesa does not support; a differing installed version is reported, not silently treated as qualified. The desktop Doctor screen shows the same catalog. This does not change a provider's native permissions or update behavior.

## Session

When Mesa's Codex SessionStart hook is installed but untrusted, open, resume, and handoff warn in text, JSON, and the app: "Review and trust Mesa's hooks in Codex; this session starts without the Mesa pointer". A different Codex SessionStart explicitly marked `source: clear` records `SessionIdentityChanged` regardless of the old SessionEnd's timing. Without that signal, `SessionIdentityAmbiguous` makes `mesa show` report a conflicting, ambiguous `/clear` or nested Codex start; neither path claims the new ID or supplies a pointer. The retained #302 logs omitted the rejected hook payload, so a distinguishable native clear signal remains unqualified.

One process in a registered project or the profile-owned General group, an agent or a plain terminal, running or resumable when the provider has a conversation. Fields: Mesa session id (8 lowercase characters, typed in `mesa stop <id>`), `kind` (`interactive`, `run`, or `terminal`), agent (`terminal` for a plain shell), project, agent session id (Claude Code session UUID, Codex thread id, or Antigravity conversation ID), `goal` (its first prompt, see Goal), `parent` (see Parent session), `after` and `pending` (see Queued session), `handoffFrom` (see Handoff), `from` (the imported item it started from, `{source, id}`, see Import), `worktree` (see Worktree), `additional` (see Additional project), `name`, `adopted` and `cwd` (see Adopted session), its tmux socket, session, and window, start time, end time once stopped, last state with its confidence and source, `context` (see Context use), last output tail, `events` (the prompts it was sent, `send`, and sent, `sent`, its agent's exit, `exited`, with the exit status or signal its dead pane showed, and a `handoff`), and `resumedFrom`/`resumedBy` links. Backed by one tmux window. Persisted as `~/.mesa/<profile>/sessions/<id>.json`. `mesa open <project> [--agent claude|codex|antigravity] [--goal <text> | --goal-file <path> | --from <item> [--goal <text>] [--no-notes] [--exact-goal]] [--parent <id> | --no-parent] [--after <id>] [--branch <name> [--base <ref>] | --worktree] [--with <project>]... [--attach]` starts one (with `--after`, queues it, see Queued session): it writes the record, then runs `claude --session-id <uuid> --mcp-config=<mesa-vault> --allowedTools=mcp__mesa-vault [<goal>]`, or `codex -c mesa.embedded=true <four -c mcp_servers.mesa-vault overrides> [-- <goal>]` (the first override keeps Codex off a running app-server daemon, ADR-0003; the others mount mesa-vault, ADR-0012), or `agy --log-file <profile-local private log> [--prompt-interactive <goal>]`, in window `<agent>-<id>` of the project's tmux session, in the project's folder or, with `--branch`, in its own worktree, with the project's enabled skills linked there first (see Skill), without a routine receipt. `mesa sessions` lists them, highest attention first (`--tree` puts children under their parent), with `alive` (the window exists, or the agent listing names the session) and `agentStatus` (the listing's `idle`, `busy`, or `waiting`, while it lists the session): every session not stopped, and those stopped within the last day; `--all` adds older ones. A session has ended when it was stopped (`mesa stop [--force]`: the agent's `/exit`, up to 5 s for it to quit, then `kill-window`; it sets `endedAt`); one whose window vanished (a crash, a reboot) is marked `done` from tmux but has not ended, so it stays on the board to resume. Mesa's tmux server also has a `pane-died` hook (set when Mesa starts the server, and on each look at a board with sessions): the moment an agent exits, it runs `mesa hook tmux pane-died <project> <window>`, which records the exit at once, `done`, or `failed` for a nonzero exit status or a signal, with source `tmux-hook` and an `exited` event. The session is not stopped by it: it keeps its place on the board, its last screen, and Resume, and `mesa stop` still removes its window. `mesa show <id>` prints one record with `alive` (as the board reads it), `instructions` (its instruction hook, ADR-0010), and `vault` (`{state: configured|missing|conflicting|unsupported, reason}`: whether its agent has mesa-vault mounted, from the record's `vaultMounted`, which the launch owner sets when a Claude Code or Codex command carries the mount, or from Antigravity's global entry, ADR-0012); Session details in the app shows both. `mesa rename <id> <name>` stores `name`, which `mesa sessions` and the Board show in place of the id (the id stays on hover, and in `--json`). `mesa rm <id> [--force] [--delete-worktree] [--delete-branch]` removes the record, its hook log, its Output log, and a Skill run's output; it refuses a live session unless `--force`, which closes its window first; `--delete-worktree` runs `git worktree remove` on its worktree and each additional project's (refused, before anything goes, for one git has locked, even with `--force`, and for one with submodules or with changes or untracked files unless `--force`), `--delete-branch` deletes their branch (refused, before anything goes, for one checked out in a worktree the session does not hold, and without `--delete-worktree` for one its own worktree still has, as git keeps a branch a worktree has checked out), and neither touches a worktree a session resumed from it has now; every refusal comes before the record goes, and `--json` says what was removed. The Board's row menu has Log (see Output log), Rename, and Remove, which confirms by listing what goes and removes only an ended session. `mesa resume <id>` reopens an ended session's conversation (`claude --resume <agent session id>`, `codex -c mesa.embedded=true resume <thread id> -C <folder>`, each with the mesa-vault mount again, or `agy --conversation <conversation id>`) in a new window as a new session, linked by `resumedFrom` and `resumedBy`. Codex picks its own thread id: its first SessionStart hook fills the record, and later events match that id. Without trusted hooks, a look at the board reads it from Codex's rollouts: the newest interactive one under `$CODEX_HOME/sessions/<local date>/` that ran in the session's folder, started after its window opened, and no session holds. `mesa send <id> <prompt> [--force] [--yes] [--from <sender> | --no-from]` types a prompt into a live session's agent (one literal chunk, then Enter, 0.3 s later for Codex, whose paste detection could take an Enter at once as a newline; the same for the `/exit` of a stop) and adds a `send` event to its record; it refuses a pane running a shell, and an agent waiting on a person, unless forced, and then asks the Guardrail, whose block `--force` passes and whose ask `--yes` (or `--force`, or a person's `y`) passes. One `--force` covers every refusal a person may override on a send, so it never sends past one check only to be stopped by the next. From another session (`--from`, else the Mesa window it runs in, as for a Parent session; `--no-from` sends as a person, and the Board's Send passes it), the prompt starts with one header line, `[mesa] from session <sender> (<project>). Reply with: mesa send <sender> "<reply>"`, so the receiver knows who asked and how to answer; the prompt itself is on the next line, so a slash command from another session is not run as one. Its `send` event names `from`, and the sender's record gets a `sent` event naming `to`; `chars` counts the prompt, not the header. An unknown sender is `not_found`; an ended one, and the receiver itself, are usage errors; and another session cannot force a prompt into a session waiting on a person, which only a person answers (ADR-0003). The Board lists each session's received prompts with their sender. `mesa hooks install|status|uninstall` manages Mesa's entries in `~/.claude/settings.json` (10 events) and `$CODEX_HOME/hooks.json` (9 events, default `~/.codex`, ADR-0003), and Antigravity's: its named `PreInvocation` hook in `~/.gemini/config/hooks.json` (ADR-0010), its `mesa-vault` server entry in `~/.gemini/config/mcp_config.json`, and the one allow rule `mcp(mesa-vault/*)` in `permissions.allow` of `~/.gemini/antigravity-cli/settings.json` (ADR-0012); every other entry, rule, and setting stays as it was, uninstall removes a file it leaves empty of all but Mesa's container, a `mesa-vault` entry the user disabled stays disabled, and a `mesa-vault` entry that is not Mesa's, or an Antigravity file Mesa cannot read, is reported as conflicting while the other agents' hooks carry on. Codex asks the user to review and trust new hooks at its next start; Mesa never grants trust. Status and Doctor report each event's recorded `trusted_hash` from Codex's config.toml at its actual group and handler positions, and `status` also says whether the tmux server has its pane-died hook; `mesa doctor` checks the agents and tmux hooks and Antigravity's mesa-vault entry (`antigravity vault`), and warns (`codex daemon`) while a Codex app-server daemon's socket is in `$CODEX_HOME`; the agent hooks run `mesa hook claude|codex`, which, inside a Mesa session only, appends the payload (secret-named keys and the home directory redacted) to `sessions/events/<id>.jsonl` and fills in the record's agent session id. In Claude Code, a `/clear` starts a new conversation in the same agent, under a new agent session id: its `SessionStart` (source `clear`) moves the record to it, and each look at the board saves the id the agent listing names for the session's pane, so hooks keep logging and `mesa resume` reopens the conversation on screen. A hook under any other id is a nested claude's, and is dropped. `kind: run` is a headless run, still a session: `mesa run` starts one (see Skill run).
Not: task, job, run (`kind: run` qualifies a session, it is not another name for one), thread (thread is Codex's word for its own id).


## Native startup mode

`mesa open --mode plan` starts Claude Code with `--permission-mode plan` or Antigravity CLI with `--mode=plan`. The session record keeps `mode: plan`; queued starts, resume, and handoff retain it. With no mode, the provider uses its own default. Codex CLI and plain terminals refuse `--mode plan` because they have no qualified Plan startup flag. The desktop New session dialog and project composer offer Plan only for providers that support it.

## Native background session

`mesa open --background` starts Claude Code with `--bg`, stores its native short background ID, and opens `claude attach <id>` in the Mesa tmux window. The job runs in a process Claude's supervisor starts, with the supervisor's environment rather than the one `claude --bg` has, so the launch carries the session's binding as settings: `--settings={"env":{"MESA_SESSION_ID":...,"MESA_PROFILE":...}}`, which Claude applies to that process and keeps through its restarts, for the mesa-vault server and the Mesa hooks (pointer and events) to read (ADR-0012). The `claude --bg` process itself gets no window variables, as a supervisor it starts would keep them for every later background job. Plan can be combined with background. The native process keeps running when its terminal view closes; opening the session recreates that view. `mesa stop` calls `claude stop` before closing the view, and `mesa resume` opens the same native background conversation under a new Mesa record. Queued starts and handoffs retain background mode. Other providers and plain terminals refuse it. The desktop session form and project composer offer it only for Claude Code.

## Plain terminal session

`mesa open <project> --terminal` starts the profile's login shell in a project checkout, or in its own worktree with `--branch`. It uses `kind: terminal` and `agent: terminal` in the session record, with no agent session id, goal, provider, context use, or skill links. The Board observes its tmux window directly; it does not ask Faro to infer a coding-agent state. Attach and stop work as for other windows. Send, resume, and handoff refuse it because there is no coding-agent conversation. The app's quick Terminal choice uses this path.

## Archived session

`mesa archive <id>...` ends each named session and sets `archivedAt`, keeping its record, output log, and worktree; with several ids it reports one item per id, and an unknown id archives none. The active Board and project session list hide it; `mesa sessions --all` still finds it. `mesa unarchive <id>` clears `archivedAt` without restarting the process. Permanent removal remains `mesa rm` and its confirmation, and the selected session's close control offers archive or permanent deletion. The sidebar's Sessions tab archives a multi-selection together (Shift-click a range, Cmd-click to toggle, then Archive from the right-click menu, or from the keyboard, Shift+Arrow or Shift+Enter to range, Cmd+Enter to toggle, then Archive N sessions from the card's More menu) behind one confirmation. A range starts at the last card clicked or toggled, else the shown session, else, for Shift+Arrow, the card it moves from.

## Workflow status

A person's optional label for a session's work: `todo`, `in-progress`, `review`, or `done`. `mesa workflow <id> <status>` sets it, and `clear` removes it; `--json` returns the record. It lives in the session record as `workflowStatus` and appears on the Board. Faro's `lastState`, confidence, attention and decision evidence remain separate; setting workflow never changes what the agent is observed doing. An absent label is unassigned.
Not: agent state, attention, Faro decision.

## Grid group

A profile-local named set of session ids for reopening live terminal tiles in the app's Grid. `mesa grid save <name> <ids...> [--project <slug>]` stores it in `config.yaml`; `mesa grid` lists groups and `mesa grid remove <name>` removes one without stopping or deleting its sessions. The Grid's project tabs filter visible tiles; switching tabs or leaving the Grid keeps terminal clients attached. An ended or missing session stays in the saved group and is reported unavailable when reopened.
Not: session group (Board grouping derives from session properties and saves no named set).

## Goal

A session's first prompt, given at start: `mesa open <project> --goal "<text>"`, or `--goal-file <path>` (read as UTF-8, otherwise unchanged), or built from an imported item with `--from` (see Import), or the Goal field of the Board's New session dialog. It reaches `claude` as one argument, `claude --session-id <uuid> <goal>`, quoted for `/bin/sh`, which runs every Mesa window whatever the user's shell. So the session starts working without anyone typing into it. A goal starting with `/goal` runs Claude Code's goal command, which keeps the agent working until its condition holds; its condition is every line after `/goal`, and a handoff's note line joins it. Such a goal is refused for Codex and Antigravity, which have no `/goal` and would take it as plain text, and when its condition is over the 4000 characters Claude Code takes, at open and at handoff. The record keeps it as `goal`, `mesa goal <id>` prints it, and the Board shows its first line under the project. A resumed session keeps its goal, but it is not sent again. A goal is refused when it is blank, starts with `-`, holds a NUL byte, or makes the command longer than the 12000 bytes Mesa passes to tmux (one tmux command holds about 16 KiB). The goal stays in the local session record; routine starts have no receipt. `mesa vault goals <project>` lists a project's earlier goals (see Project context).
Not: task, prompt (a goal is one prompt, the first), objective.

## Saved prompt

Named, profile-local text in `prompts.json` that a person inserts into a new session's Goal or a live session's composer. Insertion keeps every newline and never sends or starts a session by itself. The selected agent receives an initial Goal unchanged; its own system instructions and native configuration remain that agent's responsibility. `mesa prompts` lists entries, `mesa prompts save` adds or explicitly replaces one, and `mesa prompts remove` deletes one. A backup includes saved prompts but excludes provider credentials and vault contents.
Not: Goal (a saved prompt is reusable text, not a session's recorded first prompt until that session starts).

## Caller

The session whose Mesa window a `mesa` command runs in, read from the window's `MESA_SESSION_ID` and `MESA_PROFILE` (`callerOf`): a window of another profile, or of a removed session, is in a Mesa window with no session here. It is the default parent of a session `mesa open` starts, the default sender of `mesa send`, and, when it hands itself off, the reason its stop runs later from the tmux server. Outside a Mesa window there is none, and mesa acts for a person.
Not: parent (the parent is a link on a record; the Caller is who runs this mesa now).

## Parent session

The session another was started from. `mesa open` run inside a Mesa window of the same profile (its `MESA_SESSION_ID` and `MESA_PROFILE`) records that window's session as the new one's `parent`; a window of another profile, or of a removed session, gives none. `--parent <id>` names one, and an id that is not a session of this profile is `not_found`. `--no-parent` records none, and passing both is a usage error. The Board's New session passes `--no-parent`: a person starting one is not a session starting a child. A resumed session keeps its parent. `mesa sessions --json` gives every Mesa row its `parent` (absent when it has none) and its `children` (the ids of the sessions whose parent it is, on the board or not). `--tree` orders the rows as a tree, each with its `depth`: a row, then its children, then theirs. Siblings, and the rows at the top, rank by the highest attention in their subtree, so a child waiting on a person lifts its whole branch. A child whose parent is off the board sits under the session that parent was resumed as, else at the top, its `parent` kept. The Board shows the tree; a toggle collapses the rows under a row, and a collapsed row says how many it hides and marks one that waits on a person.
`mesa dependency <id> --parent <other|none>` changes this visual link without changing when a queued session starts. A cycle or unknown parent is refused. The Sessions screen's Set dependency dialog edits the same link.
`mesa stop <id> --descendants` and `mesa rm <id> --descendants` act on the transitive `parent` family, children before parents. `--expect=<child,...,root>` confirms the exact IDs first; if the family changed, nothing runs. JSON reports each outcome or refusal. The Sessions screen previews the same IDs and requires confirmation. An `after` queue link alone is not family membership.
Not: owner, spawner, caller (the Caller is who runs mesa, which makes it the parent by default).

## Queued session

A session waiting to start until the session it waits on is over: `mesa open <project> --after <id> [--goal ...] [--branch ...]` writes its record, `queued`, with `after: <id>`, its `parent` defaulting to that session (`--parent` and `--no-parent` still win), and `pending`, the branch and base its worktree gets when it starts, and `with`, the additional projects that each get one on that branch (`--after` with `--with`, see Additional project); it has no window, no worktree, and no agent session id yet, since it never ran. An id that is no session of this profile is `not_found`, and `--after` a session that is already over starts it at once. A session is over for its queue when it has ended (`endedAt`) or was seen `done`, `failed`, or `stopped`. No daemon: whichever signal first finds it over starts every session queued after it, through the steps `mesa open` takes, without a routine receipt: an agent's SessionEnd hook (`mesa hook claude|codex`; Claude's `/clear` or `/resume` keeps its agent running and starts nothing; Codex ends regardless of reason), tmux's pane-died hook (`mesa hook tmux`), a `mesa stop` of it, or a look at the board that finds it over, or gone, which catches a missed signal. The starter claims it first, under the record's lock (`pending.claimedAt`, with its agent session id), so two signals at once start it once; a claim older than 30 s is taken again, as a start killed mid-way left it (a SessionEnd hook has 1.5 s), keeping its id and any window it opened. A start that fails leaves it `failed`, ended, with every new worktree removed, in each project. `mesa stop` on a queued session cancels it: `stopped`, ended, and the sessions queued after it wait on what it waited on instead, so a chain keeps its order. `mesa rm` refuses a queued session until it is cancelled, as removing it would leave those waiting on nothing. `mesa sessions` shows `waiting on <id>` in place of its last output; the Board shows the same, with Cancel for Stop. Waiting on several sessions is out of scope.
`mesa dependency <id> --after <other>` changes a queued session's wait target without changing its parent. It refuses a cycle or a queue start already claimed; an already-over target starts the session immediately. `mesa force-start <id>` explicitly starts it without waiting and clears `after`. The Sessions screen exposes both actions.
Not: scheduled, deferred.

## Handoff

A session's work continued in a fresh successor, so long work never waits on a person to copy text between sessions. `mesa handoff <id> --note <file> [--keep]` copies the note to `~/.mesa/<profile>/handoffs/<successor id>.md` and opens the successor on the same project, with the same agent, in the same folder, taking over the session's worktree (and so its branch), with `parent` and `handoffFrom` the session, and a goal made of the session's own (an earlier handoff line dropped) plus `Read the handoff note at <path> first.`. Both records get a `handoff` event (`to` on the session, `from` on the successor, each with the note), and a `session` receipt records from, to, and the note; `--json` prints `{from, to, note}`. Then the session stops: at once, or, when it hands itself off from inside its own window, from Mesa's tmux server two seconds later (`run-shell -b`, running `mesa stop`), since its own stop would kill the `mesa handoff` running in it. `--keep` leaves it running, except a session in its own worktree, as two sessions never share one. A session without a goal is `usage`, a note that is not there `not_found`, and every refusal comes before anything is written. The `mesa-handoff` skill teaches an agent when and how: read its own `context.used` (see Context use) after each finished step, and at the threshold (55 unless its goal names another) write the note in four sections (Verified, with commands and results; Assumed; Left out on purpose; Blocked), hand off, and stop working. The Board's Hand off button asks for the note file.
`mesa handoff <id> --note <file> --agent claude|codex|antigravity` explicitly chooses the successor's provider. It keeps the goal, note, project, and actual working folder; the target starts with its own native mode and background defaults. The source stops only after the target window opens. The Board's Hand off dialog offers the same choice.
Not: transfer, fork, relay.

## Swap

Changing a fresh session's agent in place: `mesa swap <session> <agent>` keeps the Mesa session, its folder or worktree, its parent and name, and starts `<agent>` in a new window `<agent>-<id>` under a new agent session id, then closes the old window (the record moves first, so the old pane's death is no session's) and clears the old agent's hook log; a launch that fails puts the record back with the old agent still running. Mesa cannot carry a conversation across agents, so a session with one (a goal, a `send` event, or a `UserPromptSubmit` hook) is refused as usage, naming `mesa handoff <id> --agent <agent>`; so are a working, ended, or queued session, a terminal, a run, a Claude background session, and the agent it already runs, and an agent Mesa cannot run is `agent_unavailable`. A startup mode (plan) is not carried. Board rows say `conversation: true` for a session with one. In the app the session header's agent is a menu, `<agent> ⌄`: "<agent> (current)", then "Swap to <agent>" for each installed agent (one not installed shows disabled); Swap on a fresh session swaps it, on one with a conversation opens Hand off with that agent chosen; the menu is disabled while the session works.

## General session

A session with no registered project. `mesa open --general [--terminal]` starts in the profile home folder, records that absolute `cwd`, and groups its tmux window under the reserved `__mesa_general__` name, outside valid project slugs. It uses the profile default agent unless one is selected, without reading a project `mesa.yaml` or linking project skills into home. The app shows it under General. It can be resumed and managed by session id. Project worktrees, skill runs, queues, and handoff require a registered project. Provider trust and permission prompts are left to the provider.

`mesa open <project> --terminal --parent <id>` starts a separate child shell in that parent's actual cwd when it belongs to the same project, including a worktree. `mesa open --general --terminal --parent <id>` does the same for a General parent. The selected session's app actions can open that child terminal or a new child worktree session on its project.

## Worktree

A Git linked checkout of a registered project, created for a session with `mesa open <project> --branch <name>`, or `--worktree` for a new branch Mesa names `session/<adjective>-<noun>-<4 characters>`, or manually with `mesa worktrees create <project> <branch>`. The project must be the repository's top folder. The project Overview's Worktrees cards and `mesa worktrees list <project> --json` show Git's linked checkouts, their state, and unfinished Mesa session holders; preview, apply, and setup reruns are CLI commands. A manual worktree has no session holder until a session uses it; `mesa open <project> --checkout <path>` starts one in an existing linked worktree no unfinished session runs in, and a detached one (a recycled worktree) first gets a new branch Mesa names. The Overview's Worktree cards do the same on hover: New session, Recycle worktree, and Remove worktree, with Cleanup in the section header. Each card shows its state: `mesa worktrees list --json` gives a row its `changes` (staged, modified, untracked), `ahead` (commits the default branch lacks), and a linked one its `createdAt`; a card with a session in it opens that session on click and offers no New session, and one being removed or recycled says so. Without `--branch` or `--worktree`, a session runs in the project's main checkout. The app's New session, New worktree session, and New terminal session start one at once with no dialog and no `--agent` (the project's, else the profile default), showing a Starting session row in the sidebar until it opens.

By default Mesa puts a new worktree at `~/.mesa/<profile>/worktrees/<project>/<name>` (a `/` in the branch becomes `-`). Profile `worktrees` settings can instead put it in a sibling folder, a nested `.mesa-worktrees/` folder, or an absolute custom root. Nested folders are listed in the repository's local Git exclude file. The same location, optional fetch, default base, sparse directories, and explicitly named ignored directories apply to manual creation and session launch; none are fetched, made sparse, or carried by default. A project's `mesa.yaml` can override all of these but the location (Project override). Sparse checkout uses Git cone-mode directories, and carryover copies only ignored, untracked local directories. `--base <ref>` overrides the profile default for a new branch.

Optional profile `worktrees.setup` and `worktrees.teardown` are executable-and-argument lists. Setup runs without a shell in a newly created worktree; `mesa worktrees rerun <project> <checkout>` repeats it in an existing linked worktree. A failed setup leaves the worktree and any data it wrote for inspection and rerun. A failed session launch likewise preserves a new worktree after configured setup has run.

`mesa worktrees preview <project> [<checkout>] --action remove|recycle|trash|cleanup --json` reports the canonical path, branch and head, session references, changed, untracked and ignored files, unpublished branch state, and a token. `mesa worktrees apply` requires that token and rechecks the state. A session running in a worktree blocks every action on it. Remove refuses local work (changed, untracked, or ignored files, unpublished commits, an ended session still referencing it), which the preview marks `forceable`; `apply --force` removes it anyway (`git worktree remove --force`), as the app's Delete anyway does once the preview has listed it. It runs configured teardown, rechecks again, and removes only the checkout; its branch remains. Recycle resets a clean linked checkout for reuse: it fetches origin, then `git switch --detach` to the default branch (`origin/HEAD`, else the configured base, else main's branch), keeping its old branch, or deleting it with `--delete-branch` when Git agrees it is merged (`git branch -d`). Trash moves a linked checkout, including its local files and branch, into the profile's `recycle/` directory through Git. Cleanup asks Git to prune only missing worktree registrations after showing all of them; a partial result reports those still registered.

An existing local branch not checked out elsewhere is reused as it is, and an explicit `--base` with one is a usage error. A new branch starts from its explicit or configured base, else the branch of that name on origin, which it then tracks where Git can, else origin's HEAD, else the current branch; it tracks nothing else. Mesa claims the target path before adding the worktree, and a failed creation removes the path and only a branch Mesa made. A session record keeps `worktree: {path, branch, base}` (`base` only for a branch Mesa made). A resume uses the same worktree and refuses one a newer session holds or one whose folder is gone. Git or Mesa refusals are `usage`; a missing or unresponsive Git is `internal`. `mesa rm <id> --delete-worktree --delete-branch` removes a session's worktree and branch when allowed. Profile `worktrees.deleteBranch` (default false, Settings > Git & Worktrees > Cleanup) only pre-checks the app's "also delete branch" in Remove and Remove descendants; `mesa rm` still deletes a branch only with `--delete-branch`.
Not: checkout, clone, sandbox.

## Additional project

Another registered project a session also works in, beside its own (the primary): `mesa open <project> --with <other> [--with <other>...] [--branch <name> [--base <ref>] | --worktree]` gives the primary and each other project its own Worktree on one branch, a Mesa-named `session/<words>-<4>` one when no `--branch` is given (`--with` implies `--worktree`), and starts the agent in the primary's worktree with each other worktree as an extra folder (`claude --add-dir=<path>`, `codex --sandbox=workspace-write --add-dir <path>`, `agy --add-dir=<path>`). Codex gets `--sandbox=workspace-write` on every start, resume and fork with additional projects, as it refuses an extra folder it may not write; a configured `danger-full-access` or bypass is kept, and a configured `read-only` is overridden for that session, with the warning `Codex runs read-only in this profile; this session gets workspace-write so it can change the other projects` and the receipt of each start (open, resume, fork, swap, a handoff's successor, a queued start) kept with `outputs.sandboxOverride`. `--base` applies to every new branch; otherwise each project starts from its own default, and an existing branch is reused per repository. The record keeps them as `additional: [{project, worktree: {path, branch, base?}}]` after the primary's `worktree`; absent means none. Every `--with` is checked before any git write (registered, not the primary, named once, setup approved, the top folder of a git repository), then the worktrees are made in order; a failed launch removes every worktree and branch it made whose setup did not run, keeps and names one whose setup ran, and removes the record. Each worktree gets its project's enabled skills linked in. Its worktree is held like the session's own: `mesa worktrees list` shows the session as its holder, a remove preview is not allowed while it runs, another session on that branch in that project is refused, and a resume, handoff or swap carries it. The project, its tmux session, the board group, vault writes and receipts stay the primary's; the open receipt names the rest (`inputs.with`, `outputs.additional`), and the agent's pointer adds an `Also in projects` line. Every reader of which sessions touch a project counts it for each of its projects (`sessionProjects`): `mesa git insight` and PR events (one watch per worktree it holds, the decision receipt still the primary's), `mesa projects --sort active-sessions|last-session`, `mesa vault goals` and `session_goals`, and a vault write's `--project` with `--session` (a `save_note` in `projects/<additional>/` saves under that project). `mesa sessions` and `mesa search` show them after the project, `alpha +beta,gamma`, and the app's session cards a `+<project>` badge for each. A project's Overview (Active, Recent) and its Projects tab count include a session where it is additional, marked `from <primary>`; the Sessions tab groups it under its primary only. A queued session counts for its other projects once it starts, as `sessionProjects` reads `additional`, not `pending.with`. Refused with `--general`, `--terminal`, `--checkout`, and for an agent with no qualified `addDir`. With `--after` it is queued, `pending.with` keeping the projects until it starts, when each gets its worktree as at open (see Queued session). `mesa fork <id> --branch <name>` gives the fork a worktree on that branch in every project, each new branch from that project's worktree HEAD in the source, and its agent the other worktrees as extra folders; without `--branch` it is a usage error. `mesa rm <id> --delete-worktree [--delete-branch] [--force]` removes every worktree it holds (and their branch): before anything is removed it refuses, naming the project and path, a worktree another session holds or runs in, one git has locked (`git worktree unlock <path>` first, even with `--force`, which never becomes git's `-f -f`) and, without `--force`, one with initialized submodules (`--force` removes it with their git data) or with changes or untracked files, and with `--delete-branch` a branch checked out in a worktree the session does not hold (the main checkout, another worktree, or a registration whose folder is gone), naming where, or, without `--delete-worktree`, in its own; a git failure after that leaves the rest for a retry, which passes over what is already gone; `--json` lists the others under `additional`, and `mesa rm --descendants` passes the flags to such a descendant too. See ADR-0021.
Not: workspace, secondary project, linked project.

## Selected checkout

The registered project's root or one of its Git linked worktrees selected for Git and Files tools. It is a view and operation target, not another project or a session holder. Git must still report it as a worktree of that project before Mesa reads or changes its files. A selected checkout can be the main checkout, a session worktree, or a manually created worktree.

## Repository insight

An explicit read-only `mesa git insight <project> [--checkout <path>] --json` refresh, also in the project's Git tab. Local branch, HEAD, changed-file and worktree counts, and recent commits come from Git with an observation time. When the native GitHub CLI is available, Mesa reads at most the latest 100 PRs and shows outcomes whose head branch name matches a recorded session worktree branch; a pull request from a fork (`isCrossRepository`) never matches, whatever its branch is called. This is a branch-name link, not a claim that the session authored the PR. The result gives the CLI's availability and version, observation time, each PR's update time, and whether the 100-PR result limit was reached. No PR or CI state is changed.

## Foreign session

A live agent session Mesa did not start: a `claude` or `codex` run in a plain terminal, or by another tool. `claude agents --json` lists every live Claude Code session on the machine; Codex has no such listing, so Mesa lists the interactive Codex threads whose rollout was written in the last 10 minutes, with no status. A listed process that runs in no open Mesa session's window, and whose agent session id no open session of this profile holds, is foreign, unless another profile's records hold that id. `mesa sessions` and the board show foreign sessions among Mesa's, by attention, read-only. Each gets id `ext-<pid>` (a Codex one `ext-<thread id>`), `managed: false`, a state read from the listing alone (0.85, ADR-0003; a Codex row says none, so it is a guess at `working`, 0.5), and a project. The project is the registered one it runs in (its folder or one inside it), else a project named like its folder, else none. `stop`, `send`, `resume`, `attach`, and `goal` refuse an `ext-` id as `not_found` with "session not managed by mesa"; `mesa adopt` makes one Mesa's (see Adopted session).
Not: orphan (a Mesa session whose window vanished is still Mesa's, marked `done`).

## Adopted session

A Claude Code or interactive Codex conversation started outside Mesa that Mesa then took in: `mesa adopt <agentSessionId> [--project <name>] [--name <text>] [--no-resume]`, or Adopt on a foreign row of the Board. Mesa finds it in the agent listing, else by its native transcript: Claude Code's `~/.claude/projects/<folder>/<id>.jsonl` or Codex's interactive rollout under `$CODEX_HOME/sessions/`. It reads the actual working folder from that file. Its project is the one that folder is in, as for a foreign session; else `--project` places it; else it is `not_found`, and a `--project` other than the folder's project is a usage error. Mesa writes a record with `adopted: true`, its native id, `name` when given, else its native name, and `cwd` when the folder is not the project's own, then reopens the conversation in a Mesa window in that folder (`claude --resume <id>` or `codex resume <id> -C <folder>`), as `mesa resume` does; `--no-resume` writes the record only, and `mesa resume` opens it later. Every adoption says `end the session in its original terminal first: both hold the same transcript`, in the output and as `--json`'s `warning`, beside the record's own fields. An id that is not a lowercase UUID is a usage error; one Mesa already has is a usage error naming that session, or saying another profile has it. A resume keeps `adopted`, `name`, and `cwd`. Headless Codex rollouts are not imported as interactive sessions. Antigravity history has no qualified native source yet.

`mesa history <project> --json` and the project's collapsed Native history panel list the newest 100 native Claude Code and interactive Codex conversations whose recorded folder is in the registered checkout. The rows retain native IDs, cwd, and native names, and identify conversations held by this or another profile. Import asks the person to end the original terminal before reopening the same conversation; it never copies the transcript. Antigravity history is reported unsupported until its native CLI exposes a qualified source.

A conversation's native name is the one its agent shows: for Claude Code, the `customTitle` of its transcript's latest `custom-title` entry (a person's rename), else the `aiTitle` of its latest `ai-title` entry; for Codex, the `thread_name` of the last line for its thread id in `$CODEX_HOME/session_index.jsonl`; Antigravity has none. Names are read from the end of each file, and only for the rows shown; a Claude Code name comes only from the last 1 MiB of its transcript, so a title written only before that is not found, and a rename written before it gives way to a later AI title.

`mesa discover [--days <n>] --json` (default 30, 1 to 365) and Add project > Find from sessions in the app list what ran on this machine outside Mesa, whichever profile is open, without writing anything: the running Claude Code and Codex sessions from the agent listing, and the native conversations updated in those days (newest 300, with `total` and `truncated`), both leaving out any conversation a session of this or another profile holds, and each with its native name. Each is placed in its project folder: the nearest folder at or above its cwd, below the home folder, holding `mesa.yaml` or `.git`, a linked worktree's being its main checkout's; a cwd that is gone, or in no such folder, has none. The folders are listed with their name, whether they are registered, and their conversation and running counts; the app's Add to Mesa adopts the ticked ones (see First-run discovery). Antigravity is reported unsupported, as for native history.

`mesa history search <project> <words> --json` and the panel's Search field match case-insensitive text in native user and assistant messages, including text tool results. Provider system/developer entries and Claude sidechain replies are excluded. The search reads at most the newest 100 conversations, the last 2 MiB of each file, and 30 hits; `truncated: true` and the app's partial-results label report a limit reached. Native files remain local and unmodified. Antigravity search is unsupported for the same native-history reason.
Not: imported, attached, foreign (a foreign session is one not yet adopted).

## First-run discovery

The app's offer, at launch, to take in what already ran on this machine: the Find from sessions dialog (also reached from Add project > Find from sessions), over `mesa discover`. It opens once config and projects load, never over onboarding (whose Projects step lists the same folders, registers the ticked ones, and writes `complete`, so a fresh profile never sees the dialog on its own), when the profile's `onboarding.discovery` is `started`, or is `pending` with no project registered. The four states: `pending` (the default, never acted on), `started` (Add to Mesa began and did not finish, so the next launch offers it again), `complete` (Add to Mesa finished), and `dismissed` (Skip); Escape, or quitting mid-run, leaves the state as it was. Each unregistered folder is ticked by default and each running session is not. A running session's tick is enabled only while its folder is ticked. One that cannot be ticked has its reason in place of the tick: one in a registered folder is listed as `in a registered project` with Adopt, which adopts and reopens only that session, as `mesa adopt <id>` and the Board's Adopt do (with the adoption warning), and then reads `adopted as <id>`; one in no project folder is listed as `no project folder`, and one in a folder that cannot be added as `its folder cannot be added`, neither with a tick. The dialog's one `mesa discover` call is the run's only scan: it stats each transcript and rollout first and opens none last written before the window, and of the rest reads only the head it needs, in steps from 32 KiB, a Claude Code transcript up to its first line naming a `cwd` (at most 1 MiB) and a Codex rollout up to its first newline (at most 256 KiB). Add to Mesa writes `started`, then runs `mesa discover adopt <path> --ids <ids> [--live]` for each ticked folder in order, `--ids` naming the folder's conversations that scan listed (none when it listed none), so no folder is scanned again; only a folder whose conversations the scan, cut at the newest 300, did not list in full goes without `--ids` and is scanned on its own, and `--live` when one of its running sessions is ticked, which reopens them, found from the agent listing; it shows `Adding <name> (2 of 5)` and a bar of folders done, then writes `complete` and shows the projects registered, the sessions adopted, and each failure with its reason; Skip during a run stops after the folder being added. `mesa discover adopt <path>... [--days <n>] [--live]` registers each folder unless registered (a minimal `mesa.yaml` when it has none, as Import workspace does), then adopts, record-only (`--no-resume`, so no second agent writes a transcript still open elsewhere), every conversation of the last `days` that one discovery scan, shared by all the folders, places in it, each under its native name and with `adopted: true`; with several paths `--json` prints `{items}`, one per folder. With `--ids <id>,<id>` (one path only, and not with `--days`, which it has no scan for) it adopts exactly those conversations, each looked up on its own, without a scan: one that is not a native conversation, is held by a session, ran outside the folder, or is running without `--live` lands in `failed` with its reason (with `--live` a running one is reopened, never recorded only); with `--live` it also adopts the folder's running sessions with resume, reopening them in Mesa windows, and says the adoption warning. Each is adopted into the project its working folder is in, as `mesa adopt` places it, so a conversation from a linked worktree registered as its own project goes to that project, its item carrying `project`, and the text says `adopted <agentSessionId> into <project>`. One conversation failing is listed in `failed` while the rest go on, and the command exits 2 (see Bulk command); one receipt records the batch; a second run finds the adopted conversations held and adopts nothing new. A past conversation is then resumed from the Board like any ended session.

## Bulk command

A command acting on several sessions or conversations: `mesa archive` with several ids, `mesa stop --descendants`, `mesa rm --descendants`, and `mesa discover adopt`. It reports each item (in `--json`, one item per session, or `failed` beside what was adopted) and exits 2 when any item failed, 0 otherwise, so a script sees a partial failure while the envelope stays `ok: true` with every item. An unknown id or path fails the whole command, with its own error and exit code, before anything runs; only `mesa discover adopt --ids` lists a conversation id it cannot adopt as an item in `failed`. The app reads the envelope whatever the exit code.

## Project view

A project's sessions side by side in one terminal: `mesa view <project> [--app]`, in `terminal.app`. Mesa opens a view session (`_view-<id>`, hidden from listings) whose one window, named after the project, has a pane per session of the project with a window, oldest first. Each pane is a terminal on that session's window with a view holding only that window (ADR-0001 amendment), so typing in a pane reaches that session's agent. When the window is killed (stop, resume, or removal), its pane's client exits and the pane ends; it never switches to another session's window. The panes are laid out by the project's `mesa.yaml` `tmux.layout`, a tmux layout name (`tiled`, `even-horizontal`, `even-vertical`, `main-horizontal`, `main-vertical`), `tiled` when unset; one tmux does not know is a usage error. The view goes, with the terminals in its panes, when its terminal detaches; the sessions keep running. `--json` prints `{opened, project, sessions, layout, app}`. No session with a window is `not_found`.
Not: layout (the field), dashboard, the Board.

## Window

The tmux window one session runs in, on the profile's own tmux server (socket `mesa-<profile>`, ADR-0001). The tmux session holding it is named after the project; the window is named `<agent>-<Mesa session id>` (`claude-a1b2c3d4`). A window whose agent exited stays, dead, with its output. `mesa windows [project]` lists them, and the Doctor screen shows them. `mesa attach <session>` shows a session's window in this terminal. Each terminal gets its own view session (`_view-<id>`), grouped with the project's session: it has the same windows but its own current window. tmux drops the view when the terminal detaches, and the board and `mesa windows` never list views. Attaching to the project's session itself would switch every attached terminal to that window. `--app` opens it in the app the config key `terminal.app` names, through `open -a <app> <script>`. With `terminal.wezTermNewTab` enabled and a WezTerm window already open, Mesa uses WezTerm's CLI to add a tab to that window instead. `--print` prints the attach argv instead, and the app's embedded terminal runs that argv. Without a terminal on stdin, and with neither flag, it is a usage error. `mesa resize <session> <cols> <rows>` sizes the window to a view now, then hands sizing back to tmux's `window-size latest`, so from then on the client used last (attached or typed in) sizes it (ADR-0001 amendment). Mesa's server sets its windows up for the app's embedded terminal (SP-3): `mouse on` (the wheel scrolls tmux's history: one line per wheel report in the app's view, which sets `@mesa-wheel-lines` to 1 through `--print`, and tmux's five in every other attach), `status off`, and `set-clipboard external` (a copy goes out as OSC 52). A drag's copy is also piped to `pbcopy`, so it reaches the pasteboard in any client, Terminal.app included. In the app, Option-drag selects in xterm itself.
Not: pane, tab. A tmux session is a project's group of windows, never a Mesa session.

## Message actions

Copy and Review over a session's embedded terminal while the pointer is on it, for the agent's latest native response as `mesa review responses` lists it: Copy puts its text on the pasteboard, and Review opens the response review on it. They show only for an interactive agent session with a response, never take the terminal's keyboard focus, and do not read terminal text. `terminal.messageActions` (default true) turns them off; Settings > Terminal & Editor has the toggle.
Not: per-message actions in the scrollback.

## Output log

Everything a session's window printed, kept past the window: `~/.mesa/<profile>/sessions/logs/<id>.log`, which tmux's `pipe-pane` appends to from the window's first byte while the config's `sessions.log` is on (the default; ADR-0001). It is the raw terminal stream, escape sequences and all, and stays on this machine, never in the vault. `mesa logs <session> [--tail N]` prints it as plain text (escape sequences, control characters, and blank lines dropped; `--json` gives `{ session, path, lines }`, `path` null for a session with none: logging was off when it started, it has not started, or it started before Mesa kept output logs), and the Board's row menu shows its last 200 lines under Log. A stop, a resume, and an agent's exit (the pane-died hook) do not copy its tail into vault receipts. A log over 20 MB is cut to its last 5 MB, in place, whenever Mesa reads it. `mesa rm` removes it.
Not: hook log (the agent hooks' `sessions/events/<id>.jsonl`), `log.md` (the vault's), transcript (the agent's own).

## Session state

Where a session is right now, one of the agent's states, `working`, `waiting-permission`, `waiting-question`, `idle`, `done`, `failed`, or Mesa's own for a session whose agent never ran: `queued` (see Queued session) and `stopped` (cancelled while queued). On every look at the board, Faro classifies a session in an agent state (`classifySession`) and attaches a confidence and a source; one in Mesa's own state keeps it, at no attention, with no Decision. The rules decide, in ADR-0003's order:

- A stopped session keeps its state.
- A dead or vanished window is a process fact (0.85): `failed` with a signal or a nonzero status, else `done`.
- Next comes the latest hook event: 0.95 under a minute old or when the listing agrees, 0.8 when stale. A `SessionEnd` from `/clear` or `/resume` says nothing, since the agent goes on. A wait more than 2 s old yields to a listing that says the agent moved on.
- Then the agent listing (0.85).
- Then the tail, the pane's last 30 lines read with CCManager's Claude Code patterns, or Codex's from docs/spikes/codex.md, where a startup gate (folder trust, hook review, the resume folder picker) is `waiting-question` (0.6). The tail is read only when no hook or listing speaks; a Codex listing row never speaks.

The rules' reading is the row's state, sure or not: no model is asked, so no look waits on one (ADR-0020). A record an older Mesa saved with source `adapter` (and its `basis` hash) still loads, and the first look that reads a signal replaces it. A look never saves a state over one another look saved since it read the record. A new state is saved in the record, with the time it began: the hook event's time, else when the board first saw it. `waiting-permission` and `waiting-question` are the states that need a human.
Not: status, phase, mode.

## Context use

How much of its context window a session has used, as the record's `context: {used, window, at, source, model?}`: `used` in percent of `window` tokens, as of its agent's reply at `at`, with `source: transcript` (docs/spikes/context-use.md, ADR-0003's #70 amendment). When the native transcript names the model that produced the reading, `model` carries that exact ID. Mesa reads the Claude Code transcript of the session's agent session id from its end: the last main-chain assistant message's input, cache-creation, and cache-read tokens, as the status line counts them; it reads no message content. `window` is the model's native window, from its id: 1M for Opus 4.7 and later, Sonnet 5 and later, and Fable, 200k for other Claude models, held to 200k when `CLAUDE_CODE_DISABLE_1M_CONTEXT` or a third-party provider (`CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY`) is set in the environment claude runs with or in Claude Code's settings `env`. The field is absent while there is no reading: no transcript, no reply yet, a compaction since the last reply, or a model whose window Mesa does not know. Each Stop hook (`mesa hook claude`) reads it, and `mesa show` reads it again; a reading taken at a Stop can trail by one request, and one taken at rest is exact to the status line's rounding. `mesa sessions` shows it as `ctx <n>%` (`ctx -` with none), and the Board as a bar, amber from 55% and red from 60%.
Codex reads the exact native thread rollout's last `token_count.info.last_token_usage.total_tokens` (or `input_tokens` for older rollouts) against that event's `model_context_window`, recording the event timestamp and `source: transcript`. The last-turn total includes cached input and the compacted context after `/compact`; cumulative thread billing is not used. `mesa show` refreshes context after it learns a new native thread ID. With no completed turn or no recorded window, context is unknown; Antigravity context use is unsupported.
The same context reading carries the native model and per-turn effort when present: Claude Code's last main-chain assistant message, or the Codex `turn_context` before its last token count. The selected session details show those facts with the reading's source and timestamp; absent fields remain Unknown.

Not: context (alone, which the Composition root avoids), tokens, usage.

## Usage ledger

Profile-local normalized token readings from native Claude and Codex records, stored in `~/.mesa/<profile>/usage.json` independently of vault receipts. Each reading names its Mesa and native session, provider, model, time, token categories, and price version; an unavailable reading or price remains Unknown. Cost is an estimated standard API list price, not account billing. `mesa usage --json` and the app's Usage view show session and aggregate totals, daily UTC buckets, and informational cost alerts. Source file stamps let repeated reads skip unchanged native records.
With the config's `sessions.statusLineCost` on, each interactive Claude session Mesa starts, resumes, or forks gets a per-launch `--settings` statusLine running Mesa's own `mesa statusline` (Claude's settings files are never written). It reads Claude's status line JSON on stdin, runs the user's own statusLine command (the project's `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`) with the same stdin, and prints its output with ` · $0.27 est.` at the end, the calling session's (MESA_SESSION_ID) estimated cost, counted as this ledger counts it but from the session's own tally (`sessions/costs/<id>.json`), which reads only the lines its transcripts gained since the last look (a transcript rewritten rather than appended to, by its size, mtime, and the bytes before the last read, is counted again), never reads or writes the ledger, and goes with `mesa rm`; an unknown cost, or any failure of Mesa's, prints the user's line alone, and it always exits 0. The user's command runs with `MESA_STATUS_LINE=1`, under which `mesa statusline` (of any mesa) prints nothing, and the user's settings follow `CLAUDE_CONFIG_DIR` when Claude's environment sets it.
Not: Context use, billing, receipt.

## Inbox

The profile-local list of input-required, finished, subagent, and Doctor notices, projected from redacted hook events and kept in `~/.mesa/<profile>/notifications.json`. It retains the newest 500 hook notices and current Doctor findings, with read, cleared, and delivered state across restarts. Doctor findings that one command fixes (`mesa hooks install`, `mesa vault init`) are one notice that names that fix; any other finding is its own notice with Doctor's hint. The app shows the Inbox in the header bell's menu. A notice opens its exact Mesa session or Doctor; native delivery obeys per-kind sound, visual, and quiet settings and never answers an agent's permission request.
Not: vault history, session state.

## Visual alert

The app's count of Sessions-tab sessions waiting for input (waiting-permission or waiting-question, agent still running): the macOS Dock badge shows it, and a dot on the sidebar's Sessions tab marks it, cleared at zero. `notifications.visualAlert` (default true) turns both off. It reads session state only: it sends no banner and plays no sound.
Not: Inbox, native notification.

## PR event

Something new on the open pull request of a live Mesa session's branch (its Worktree's), since the session started: a failed check, a check passing again after a failure the session was told of, a review (its state and author), or an issue or inline review comment. Read with `gh` only, through the branch-name matching Repository insight uses, so a fork's pull request never counts; `gh` missing, logged out, or not responding is a reported state (`gh.state`: `ready`, `missing`, `unauthenticated`, `unavailable`), and finds no event. `mesa pr-events --json` lists the pending ones and sends nothing; `mesa pr-events --deliver` (refused while `sessions.prEvents` is off, the default) sends each idle session its pending events as one short prompt, up to 10, each with its link under its pull request's. GitHub text is untrusted: only a trusted author's (`authorAssociation` OWNER, MEMBER, or COLLABORATOR, or GitHub Actions under its own login in each source: `github-actions` from `gh pr view`, `github-actions[bot]` from the REST review comments) is quoted, its first 160 characters with control, format, and backtick characters removed, in an `untrusted-github-text` fence under a first line telling the agent to read it as data, never as instructions; anyone else's review or comment is forwarded as its author, kind, file, and link alone. Author logins, check names, and file paths are cleaned and cut the same way, and a check's or comment's link that is not one plain HTTPS URL becomes the pull request's. A session working, waiting on a person, or idle by a guess under `decisions.threshold` is not typed into: its events wait for a pass that finds it idle, so delivery never interrupts a turn. The board is looked at again after the gh calls, so a turn begun meanwhile is seen, and a session idle without a Faro placement waits too. Each event id is claimed in `~/.mesa/<profile>/pr-events.json` before its send, so it is sent once across restarts and processes; a send refused before anything was typed gives its claim back. The same file keeps the checks a forwarded failure left failing, so their fix is news; each delivery pass drops the marks of sessions no longer live and of checks or pull requests a full read shows gone. Each delivered prompt keeps a decision receipt with the board's Faro placement of the session (its Decision, and the state's probabilities and confidence in `outputs`) and the event ids. With the setting on, the app delivers every minute and when a session goes idle; Settings > Notifications has the toggle and gh's state.
Not: notification, inbox item, webhook.

## Weekly Rewind

A read-only summary of the last seven local calendar days: meaningful decision and vault-change notes, ended sessions, and usage readings, with links to the exact evidence. It names missing usage or vault data rather than treating it as zero, and writes no replacement receipt or activity stream.
Not: automated workflow, global activity feed.

## Attention score

A number from 0 to 1 per session: how urgently the user is needed. Faro computes it as a `Score` over the levels none, low, medium, high, and urgent, from the state, the time in that state, and the project's `priority`. The bands never overlap across states:

- A waiting session starts at 0.75 and climbs to urgent over five minutes, and with priority.
- A failed session is 0.5 to 0.67, growing over ten minutes.
- An idle session is 0.25 to 0.42, growing over ten minutes.
- A done session is 0.25.
- A working session is 0 to 0.125.
- A stopped session is 0.

So a wait always outranks every other state. The board sorts by it, highest first.
Not: priority, urgency, rank.

## Board

The app's Sessions tab opens the selected live or recoverable Mesa session. With none, it shows a first-message composer and project picker; without visible projects, only Add project appears. If the profile has not been initialised, or `onboarding.status` is `active`, the app opens onboarding instead, four steps in order: Vault (Obsidian's vaults from `mesa obsidian vaults`, most recent first, or a new folder at `~/Documents/Mesa`, or another one; Continue runs `mesa init --vault <path>`, the one place a profile is created, which lays the vault out), Requirements (tmux and at least one agent, each missing one with Install, `mesa doctor install <name>`, and Mesa's hooks with an explicit Install hooks; Skip for now leaves the hooks for Settings), Projects (First-run discovery's folders, most conversations first, the top three ticked, plus any folder picked; at least one project), and First session (a project and an installed agent, then Start session, or I'll do it later). After Vault the step is `onboarding.step` plus one, so leaving resumes there; the last step writes `onboarding.status: complete`. Settings, General, has Run again and the command that links `mesa` onto a terminal's PATH. Sessions the app starts find `mesa` without that link, since the app puts its own folder first on PATH. A failed project lookup shows its error and Retry projects rather than an indefinite loading state. The composer uses `mesa open` in the selected project's main checkout with its configured agent. Sessions project headings expand or collapse their session groups; project workspaces open from the Projects tab. The desktop has no separate Board view. Command palette navigation, I'll do it later in onboarding, and the Sessions shortcut open the Sessions workspace; the stored shortcut key remains `shortcuts.board` for compatibility.

The Session Board remains the core/CLI presentation of every session across every project, highest attention first: `mesa sessions` returns id, project, agent, state, confidence, attention, context use, running time, and last output; `--json` includes each row's decision probabilities. `--tree` nests children under their parent. Existing `board` profile settings and `mesa board --json` presentation groups remain available to CLI callers; list/cards/workflow layouts and controls are absent from the desktop.

Selecting a session in the app opens its embedded terminal, xterm.js over a pty running `mesa attach --print`'s argv. A tmux copy reaches the pasteboard, Cmd+V pastes, and Close ends only the tmux client. Session actions include Send, Open terminal, Stop (Cancel for a queued session), Resume, Hand off, and Log, Rename, and Remove in the action menu. Terminal grid keeps several clients visible together and supports saved groups.

The app refreshes sessions every 2 s and after actions, one look at a time. Another screen hides the session workspace instead of closing its terminal clients. Confirmations disappear after a few seconds; warnings and failures remain as alert toasts until dismissed. None of the terminal-client state outlives the app.
Not: dashboard, overview, list.

## Skill

A folder with a `SKILL.md` that either agent can load; its frontmatter names it (`name`, the folder's name) and says when to use it (`description`). Repo skills live in `.claude/skills/` (Claude Code) and `.agents/skills/` (Codex). Skills Mesa ships live in the repo's `skills/`, the library: `mesa`, which teaches an agent to drive Mesa (its workflows, the window variables, and `mesa help --agent` for the rest), `mesa-handoff` (see Handoff), `mesa-vault`, which teaches the vault's note conventions (project hubs, one-topic wiki notes, the index, links, where session writes land, locked notes, and that routine events are never saved) and the `mesa-vault` tools with their `mesa vault ... --json` commands, `session-summary`, `project-brief`, `import-notes` (see Import), and `obsidian-markdown`, `obsidian-bases`, `json-canvas`, and `obsidian-cli`, copied unchanged from kepano/obsidian-skills (MIT; each folder's `NOTICE` names the commit, and the em dash check skips those four folders); a skill is enabled for a project when the profile's `skills` list (`[mesa, mesa-handoff, mesa-vault]` in a new profile; an existing profile's list is never rewritten), or the project's `mesa.yaml` `skills` extras, name it. `mesa skills list [project]` prints `[{name, source, enabled, description}]`: the library's skills (`source: mesa`), and with a project its own too (`source: repo`). `mesa skills sync <project>` links each enabled skill into the project's `.claude/skills/<name>` and `.agents/skills/<name>` (a symlink into the library), removes the links Mesa made for skills no longer enabled, and never touches an entry it did not make: an entry of the project's own where a Mesa skill would go is a conflict, left alone; `--json` prints the diff (`added`, `removed`, `kept`, `conflicts`, `unknown` enabled names). A link is Mesa's when it resolves inside the library, or when an earlier library made it (absolute, to `<folder>/skills/<the same name>`, and gone, as a deleted checkout's, or beside that folder's own `mesa` skill, as another checkout's): sync repoints such a link at this library, or removes it, and a link the user made elsewhere stays a conflict. A skill folder that links to the other (`.claude/skills` to `.agents/skills`) is one place. Mesa's links are this machine's, so sync lists them in the repository's own exclude file (`.git/info/exclude`, shared by its worktrees): git never shows them, and a worktree with only Mesa's links in it is clean. Every start of a session (`mesa open`, `mesa resume`, `mesa adopt`, a handoff's successor, a queued start) syncs into the folder the agent runs in (the project's, its worktree, or an adopted session's own) before the window opens; a sync that fails is a warning, and the session opens anyway. An individual project's Skills workspace lists and manages its skills; the standalone project table and global skills overview are absent.
Not: plugin, command, tool, prompt.

## Skill run

A skill run headlessly by an agent, in a session of kind `run`: `mesa run <skill> (--project <p> | --session <id>) [--agent claude|codex|antigravity] [--timeout <seconds>] [--yes] [--force] [-- <args>]`. The skill must be one `mesa skills list <project>` shows enabled, or one of Mesa's pipeline skills (`PIPELINE_SKILLS`, `skills/library.ts`: `import-notes`), which is enabled and linked for its own run only; one it does not show, or shows not enabled, is a usage error before anything starts, as is a timeout under one second, and an unknown project is `not_found` and an agent Mesa cannot run `agent_unavailable`. Last before anything starts, the Guardrail checks its prompt, `/<skill> <args>`: its ask passes with `--yes` (or a person's `y`), its block with `--force`, and a run it stops opens no window and writes no record, only a `blocked` skill receipt. It starts as every session does (the record, the folder checked, the project's enabled skills linked in, then its window `<agent>-<id>`), with `/<skill> <args>` as its goal (the words after `--` are the skill's, flags or not) and the Caller's session, if any, as its parent. The window runs `exec claude -p '/<skill> <args>' --session-id <uuid> --output-format json --permission-mode <run.permissionMode> --mcp-config=<mesa-vault> --allowedTools mcp__mesa-vault [<each rule>] </dev/null >~/.mesa/<profile>/sessions/runs/<id>.json` (that line is what must fit tmux's command): stdin closed unless `--session` supplies its private log input, stdout (claude's JSON result) in the profile and never in the vault, stderr on the pane and so in its Output log, and the pane's pid and exit status claude's. It starts `working` at 0.85: a headless agent has no prompt to wait at. Claude Code's listing names a running `claude -p` as it does any session (`busy`, and `idle` in its last moment), so the board reads a run from there too. Mesa looks at the pane every second until claude exits, then reads the result, closes the window, and ends the session, `done` when the result is ok and `failed` otherwise (source `mesa`), with its `exited` event; what was queued after it then starts. tmux's pane-died hook ends a run the same way, so a run whose `mesa run` was killed still ends, and leaves no dead window; whichever sees the exit first ends it, and the other reads the same result from the same files (the result, and the Output log) and the exit the record keeps. The result is `{ok, output, agentSessionId, costUsd?, durationMs, reason?}`. Claude Code supplies its `result`, `session_id`, `total_cost_usd`, and `duration_ms`; Antigravity supplies `response`, `conversation_id`, and `duration_seconds`. Antigravity's headless `SUCCESS` with an empty response is a failed Mesa run, since a soft-denied tool can produce that result and there is no text to land. It is not ok, with the reason, when claude reports `is_error`, stops early (a `subtype` other than `success`), exits nonzero or by a signal, or leaves no result that reads; the reason is claude's own words, else why the output does not read, how claude exited, and the last line of its Output log (its stderr; none with `sessions.log` off). `mesa run` prints the output, then `done` or `failed (<reason>)` with the session, the agent session id, the time it took, and the list price; `--json` prints the result with `session` and its `receipt`; it exits 1 when the result is not ok. Past `--timeout` (1200 s, 20 minutes, by default) Mesa closes the window, ends the session `failed`, and the command fails with `timeout` (exit 9, the session in `details`). The run result and local session record retain status, duration, agent session id, and output path; routine starts and finishes create no receipt. A failed run keeps runFailure in its record, so competing hook/wait completion cannot turn a stop or timeout into success. `mesa sessions` lists a run among the other sessions, its agent as `claude (run)` or `codex (run)`, and the Board badges it `run`, with no Send or Hand off: `mesa send` and `mesa handoff` refuse a run as a usage error, since its agent reads no input and ends by itself. `mesa rm` removes a run's result and any private input file with its record (`runOutput` in `--json`). Skills are invoked from a session terminal; the app has no Run skill launcher.
With `--agent codex`, the same run owner uses `codex exec --json -C <folder> -c approval_policy=never -c sandbox_mode=workspace-write '$<skill> <args>'`, redirected to the same input and output files. The goal and Guardrail prompt use `$<skill>` to invoke the skill Codex loads from `.agents/skills/`; stdin is appended by Codex as a `<stdin>` block. The profile's `run.permissionMode` and `run.allowedTools` apply only to Claude. Codex's `exec` carries the same four mesa-vault overrides as its start, `approve` included, as `approval_policy=never` fails an MCP call otherwise (ADR-0012). Codex uses its normal skill/config loading and workspace-write sandbox with no approval prompts; it never bypasses hook trust. Its result reader takes the thread id, last agent message, completion token `usage`, and fatal errors from exec JSONL; warning items do not fail a completed turn. Mesa measures duration from start to end, stores the native thread id in the record, and keeps `usage` in the result, with no `cost`. Nonzero exits and stderr-only startup failures remain failures.

With `--agent antigravity`, the same run owner uses `agy --print '/<skill> <args>' --output-format json` and reads its conversation ID, response, duration, and usage. Native Antigravity permissions remain in force: a tool requiring approval is soft-denied in headless mode. A `SUCCESS` result with an empty response is a failed Mesa run and lands no note; stderr explains the denial. The profile's Claude permission flags are not passed to Antigravity.

A pipeline skill's run cannot write the vault, as core lands its output (ADR-0006): Claude's command adds `--disallowedTools 'mcp__mesa-vault__save_decision' 'mcp__mesa-vault__save_summary' 'mcp__mesa-vault__save_note'` before `--allowedTools`, a deny that wins over the server's allow, and Codex's adds `-c mcp_servers.mesa-vault.disabled_tools=["save_decision","save_summary","save_note"]`. Antigravity mounts mesa-vault from its one global entry and takes no per-run tool rule, so its run keeps the save tools, and only the skill's own instruction keeps it from saving. A pipeline skill's run is refused before it starts while an entry of the project's own holds the skill's name in its skill folders, as the agent would load that instead of Mesa's.

Not: job, task, headless session.

`mesa run session-summary --session <id>` is a skill run about an existing session (`about` in the run record). Its project comes from that session; a different explicit project is refused. The last 1000 nonblank output lines, cleaned and redacted, go through a private input file to the agent's stdin, removed at completion. The log contents are evidence, not instructions. Core writes the returned summary to `wiki/sessions/<id>.md` through `writeNote`, with session, project, run, and completion `endedAt` frontmatter; a changed body gets one `vault-change` receipt and linked `log.md` entry. This is the skill's output landing (`skills/landing.ts`), shared by the hook and waiter and retry-safe; `mesa vault save summary` lands a session's own summary through it (see Session write). Locked notes remain untouched. Run it from a session terminal when a summary is wanted. A result may include `note`, its vault-relative path.

`mesa run project-brief --project <name>` is a skill run on a registered project. Its agent reads the README, `mesa.yaml`, and twenty recent commits and returns Purpose, Stack, How to run, and Open threads sections. Core lands those sections in `projects/<name>.md` through `writeNote`, with `type: project`, the registered repo path, and `updated` frontmatter, then appends to `log.md`. A person can preserve blocks across reruns by enclosing each in two identical `<!-- keep -->` markers; core retains their bytes and order after the refreshed sections. Invalid or unmatched markers leave the existing note unchanged and warn on the run. Run it from a session terminal when enabled.

## Instruction file

A Markdown file a provider reads for standing instructions, already on disk: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `AGENTS.override.md`, and the `.md` files in a provider's own rules folder (`.claude/rules/`, `.agents/rules/`, `.agent/rules/`, Antigravity's `config/rules/` and its plugins' `rules/`), in a project, in each provider's home (`CLAUDE_CONFIG_DIR` and `CODEX_HOME` when set, as the agents read them; `agents/<agent>/paths.ts` owns each path), or from a provider plugin. `instructionInventory` (`instructions/inventory.ts`) lists them as `{id, name, path, scope, providers, writable, readOnlyReason?}`, `scope` being `project`, `global` or `plugin`; a plugin's file or a symlink is read-only. `mesa instructions list|read|write [--project <p>] --json` lists, previews and saves them, a save only when its read revision is current, through the same checked path as Files; a project's Instructions tab does the same. Mesa never creates one. The "rule" in a Faro rule (the rules backend, `decisions/rules.ts`) and in an Automation rule (`automations/rules.ts`) is not this, and neither is the Session instruction pointer a SessionStart hook gives an agent (ADR-0010).
Not: rule, rules file, prompt, Skill.

## Receipt

A markdown note with YAML frontmatter in the vault's `receipts/YYYY/MM/`, kept for a deliberate decision with rationale (Mesa's own included: forwarding PR events into an idle session, see PR event), a material Guardrail block or override, a session started with launch flags that turn off its agent's permission checks or sandbox (a `guardrail` receipt whose `outputs.dangerousFlags` names them) or whose read-only Codex sandbox Mesa widened for its additional projects (`outputs.sandboxOverride`), or a substantive vault note change, or a Connection made or removed (`mesa sources connect` and `disconnect`, naming the Source and its sites, never a token or the account), or an Import (a `vault-change` listing each item, its snapshot, and its note). New receipts have `kind` (`decision`, `guardrail`, `vault-change`, or `connection`), as well as the historical `type`, a ULID `id`, `status`, redacted `command`, the calling Mesa session as `actor` when known, and relevant Faro probabilities. Ordinary session lifecycle, sends, polls, configuration, retries, and no-op note writes produce no receipt and no warning. Raw terminal tails remain in local output logs. Older receipts without `kind` remain readable. `mesa receipts` lists newest first, with `--project`, `--session`, `--kind`, `--type`, and `--limit` filters; `mesa receipts show <id>` reads one. Project and session contexts in the app show the relevant entries and open changed vault notes directly (a saved decision's note too: any receipt's `outputs.target`); there is no global feed. Schema and historical examples are in `docs/receipts.md`.
Not: session event, output log, activity feed.

## Session write

A decision, session summary, or note a session saves in the vault: `mesa vault save decision|summary|note ... --json`, each printing `{path, changed, receipt}`, over core's `vault.saveDecision`, `vault.saveSummary`, and `vault.saveNote` (`vault/session-writes.ts`), which the `mesa-vault` tools call too. A decision (`--project <p> --title <t> --decision <d> --rationale <r> [--probability <option>=<p> ...] [--confidence <c>] [--session <id>]`) lands in `wiki/decisions/<YYYY-MM-DD>-<slug>.md` (another decision of that title and day, one whose title, decision, rationale, or project differs, gets `-2`, `-3`, and on, never the first one's note) with `type: decision`, its project and session, the probabilities and confidence when given (each from 0 to 1), and a link to its project hub; its receipt is a `decision` one keeping the title, decision, rationale, probabilities, and confidence in `inputs`. A summary (`--session <id> (--text <s> | --file <f>)`) lands in `wiki/sessions/<id>.md` through the session-summary landing, as a run's does, with a `vault-change` receipt. A note (`--title <t> (--text <b> | --file <f>) [--path <p>] [--project <p>] [--session <id>]`) lands in `wiki/notes/<slug>.md`, or at a path under `wiki/` or `projects/<project>/` (`.md` added when missing; the folder names its project), headed by its title unless its text starts with one, with a `vault-change` receipt; anywhere else (`raw/`, `receipts/`, `daily/`, a top-level note, the project hub, a vault internal, or out of the Vault scope) is a usage error. A new decision or note gets one `index.md` line, `- [[<note>]]: <title>`, which is bookkeeping and records nothing. A title is one line (its newlines collapse to spaces, as a log line's do). Texts are redacted as a run's output is, and a `--file` is read from the working directory. The session is `--session`, else the Caller when it is on the project, and the Caller is the receipt's `actor` either way; a named project must be registered. Under the vault lock, a save whose note already says the same (its body and its own frontmatter: `created`, `updated`, and `source` are `writeNote`'s, so times alone are no change) writes nothing and returns `changed: false` and `receipt: null`, only putting back its latest receipt's log line when an interrupted append lost it; when no receipt names the note at all (a save interrupted after its write), it records the missing entry and index line once, with `changed: true`. A changed one writes the note and one receipt linked from `log.md`. A save never replaces a `locked: true` note, nor one Mesa did not write (no `source: mesa`): both are `locked` (exit 8, `details.reason` `note` or `not-mesa`) and leave no receipt. A session-summary run still lands over a note Mesa did not write, as it did before: the person asked for that run. An update keeps the blocks between paired `<!-- keep -->` markers of the note it replaces, the vault's mark for sections a rewrite leaves alone, a person's or a later import's. The vault must be laid out (`not_found` otherwise). The app's project and session Decisions and vault changes show each saved entry, a decision with its rationale, probabilities, and confidence, opening its note in Obsidian.
Not: log entry, import, Receipt (a save has at most one).

## Decision

One call to Faro: `decide(state, questions)` returning one answer per question with a probability distribution and a confidence. Question primitives: `Choice` (pick one of 2 to 255 options), `Score` (a position from 0 to 1 on an ordered rubric of 2 to 10 levels), and `Noul` (yes or no as one calibrated probability, with no separate confidence). Fixed in ADR-0004. A Decision keeps the questions, the answers, the backend that answered (`rules-fallback` when the named backend was asked and failed), what the call cost (`costUsd`, when a backend reports one, for information), when, and how long it took. Each decision site brings its own rules backend, which answers first; the backend the profile names is asked only when the least sure answer is below `decisions.threshold` (ADR-0003). `mesa decide` asks from the command line (questions on stdin, even answers, since no rules know them) and writes a decision receipt containing its questions, state, answers with probabilities, latency, and optional cost. For a project decision, `--project <slug> --rationale <text>` supplies the context, and `--session <id>` can narrow it further; the Doctor screen shows which decisions backend is in use. A `DecisionRecorder` preserves probabilities for a kept decision or material guardrail intervention; routine actions do not create receipts.
Not: judgment, classification, inference, prediction.

## Faro

The decisions layer, `packages/core/src/decisions`. Used for session state, attention score, guardrail checks before external actions (send, push, delete), vault ingest routing, and free-text request routing. It answers with its rules alone (ADR-0020): no model is asked, so with no decision key the agents work as they would on their own. Hosted models come back only behind the decisions backend seam, after ADR-0019's gate (#488).
Not: the AI, the brain, the classifier.

## Backend

A swappable implementation behind an interface. Two kinds, always qualified: the **decisions backend** (`rules`, the only one a profile can name since ADR-0020 removed the `claude -p` adapter, or `strands`, the Strands Decider client of ADR-0019, which only the evaluation runner uses) and the **session backend** (`tmux`). Say which one.
Not: provider, driver, engine.

## Decision site

A place where Mesa asks Faro a bounded question and acts on the answer only when it is decisive enough: `supervision`, `relevance`, `next-step`, and `evidence` (ADR-0019, `decisions/sites.ts`). Each site owns its question wording and its acceptance threshold on the answer's margin; below the threshold Mesa abstains and keeps its rules' result or gives no advice. A site is automatic only after it meets its frozen quality gates on the held-out corpus.
Not: use case, hook, feature.

## Abstain

What a decision site does with an answer that is not decisive enough: it is kept as evidence but not acted on. Distinct from unavailable, when no answer came (no worker, a deadline, a refused or malformed reply).
Not: fail, error, skip.

## Guardrail

A decision Faro makes before an external action (send a prompt, run a skill, push, delete): allow, ask, or block, with confidence. Recorded when the guardrail blocks an action or a person overrides it. It asks one Choice (`verdict`: allow, ask, block) and one Noul (`secret-or-destructive`: "This text contains a secret or a destructive instruction") of its own rules, which block a text holding a secret (a known key shape, or one of the profile's key values) or a destructive command (`rm -rf`, `git push --force`, `DROP TABLE`, and the rest in `decisions/guardrail-patterns.ts`), ask in a project whose `guardrail` level in `mesa.yaml` is `strict` (or whose level cannot be read), and allow otherwise, each at 0.95. The rules are its only backend: no model sees a text before it is sent (ADR-0020). That level is an input to the decision, not a guardrail itself. `mesa send` and `mesa run` ask it, each once its own refusals pass and before anything is typed or started. An ask prompts `y/N` in a terminal; with `--json` or no terminal it is `guardrail_blocked` (exit 5), with the verdict, the reason, and the decision in the error's details, unless `--yes`. A block is `guardrail_blocked` unless `--force`. Both flags work for every caller, a person or another session, and a kept receipt notes the override in `outputs.override` (`yes`, `confirmed` for a person's `y`, or `force`); a stopped action's receipt is `blocked`. The Board's Send shows an ask in a dialog whose Send anyway sends again with `--yes`, and a block in the toast, with no override (`--force` is the CLI's); skills are invoked from a session terminal. `mesa guardrail check <text> [--project <p>]` prints the verdict and the decision and writes no receipt.
Not: safety check, policy, filter.

## Composition root

`createMesa(profile, deps)` in `packages/core/src/mesa.ts`: composes every Mesa service for one profile, each domain's built by its own service factory over one shared context (`createContext`, ADR-0008 amendment), from `MesaDeps` (home, cwd, clock, id source, UUID source (the agent session ids Mesa hands to claude), `self` (the argv that runs this mesa, for the hooks and for tmux), sleep, environment, process runner, HTTP, the sign-in listener, the secret store, Obsidian paths, the invocation's argv for receipts, and `skillsDir`, the skill library). The CLI entrypoint (`packages/cli/src/mesa.ts`) builds the real deps; tests build them with `testDeps`. The app never builds them: it reaches Mesa through the bridge, and its entrypoint `main.tsx` only picks the real bridge and platform (dialogs, terminals, the pasteboard). ADR-0008.
Not: container, context, app.

## Seam

A place where Mesa's behaviour can change without editing the code there: the process runner, the clock, the id source, the UUID source, the home directory, the environment, the sleep, HTTP, the sign-in listener, the secret store (the macOS Keychain), the app's bridge and its platform (dialogs, terminals, the pasteboard). Each seam has a real implementation and a test one (`@mesa/core/testing`, `renderWithMesa`). Say implementation, not adapter: `adapter` was a decisions backend (removed by ADR-0020).
Not: boundary, interface (the interface is what a caller must know; the seam is where it lives).

## Bridge

The app's seam to the mesa CLI: a function from an argv to the envelope mesa printed. The real one calls the Rust `run_mesa` command; tests pass a fake. The app's client is built over it.
Not: IPC, API, backend.

## Source

An outside tool whose items a project imports into its vault: Atlassian (Jira and Confluence) and Notion; ClickUp may come later. One row each in `SOURCES` (`packages/core/src/sources/sources.ts`), with a matching row in the Broker's providers table. A public web link is not a Source: it needs no sign-in.
Not: integration, provider (the Broker's word for a vendor's OAuth app), connector.

## Connection

A profile's signed-in Source: its access and refresh tokens, their expiry (none for Notion's, which refresh on a 401), the sites they reach (Notion's: its one workspace), and a status (`connected`, or `needs-reconnect` once the Source refused the refresh token, revoked or expired), one macOS Keychain item per Source under service `mesa.<profile>.sources`. Nothing about the person is stored: `mesa sources list` reads the account live, and leaves it out when that read fails. `mesa sources connect <source>` signs in through the Broker; `disconnect` deletes the item. Tokens never reach argv, config, the vault, receipts, or logs. Every call to a Source's API goes through one authorized fetch (`authorizedFetch`), which refreshes and rotates the tokens, and waits out a rate limit (a 429, or a 503 with Retry-After) as Retry-After asks, at most a minute, three tries in all. Settings > Connections lists them. ADR-0014.
Not: account, login, integration.

## Broker

Mesa's OAuth broker, `apps/broker`: a Cloudflare Worker that holds each Source's client secret, sends the browser to the vendor's sign-in, relays the vendor's answer to Mesa's loopback listener (`/callback/<source>`, its `state` naming the port), and exchanges or refreshes tokens. It never sees Source content or API calls, and stores nothing. Mesa's hosted one is the default; `MESA_BROKER_URL` points at a self-hosted one. ADR-0014.
Not: relay, proxy, auth server.

## Context tab

The project screen's tab for bringing source material into the project: connected Sources, the Picker, a pasted link, and the project's imported items. Import remains the action and CLI command; Context names the section. This is distinct from Project context, the bounded vault overview a session reads.

## Import

Bringing an item from a Source, or a public web page, into a project's vault: `mesa import <link>... --project <p> [--no-notes]`, or the project screen's Context tab (a card per Source, to Connect, Reconnect, or Browse it in the Picker; a paste-a-link box, which takes any public web page too; a Write notes toggle, on by default; and the project's imported items, each with Start session, Refresh, and Open in Obsidian). A link is a Jira issue's URL (`/browse/<KEY>`) or bare key (which needs exactly one connected Atlassian site), a Confluence page's URL (`/wiki/spaces/<space>/pages/<id>`), a Notion page's or database row's (`www.notion.so` or `app.notion.com`, its id the last 32 hex or `?p=`; docs/sources/notion.md), or any other http(s) URL, a web page; an Atlassian link resolves through the connected site its host names (`sources/links.ts`). Every link resolves, and every item is fetched (only GETs: Jira's issue with `renderedFields` and every page of its comments; Confluence's page body as `view` and its ancestors, followed by `parentId`; a Notion page and its content from Notion's own Markdown endpoint, a row's properties listed above it; a web page with no sign-in, cleaned by Defuddle), before anything is written, so an unsupported, unconnected, missing, or unshared link stops the import with nothing written. One owner turns HTML into Markdown for both (`lib/html-markdown.ts`). Each item then gets a new snapshot through `writeNote`, `raw/<source>/<id>/<YYYY-MM-DDTHHmm>.md` (`source` is `jira`, `confluence`, `notion`, or `web`; `id` the issue key, the page id (Notion's 32 hex), or a slug of the URL; `-2` and on for another fetch in the same minute), with frontmatter `project`, `source`, `url`, `id`, `title`, and `fetched`; an earlier snapshot is never changed. With Write notes on, an import takes at most 50 items (their `<snapshot>=<note>` arguments must fit the run's tmux command), and one Skill run of `import-notes` (a pipeline skill: enabled and linked for its own run whatever the skills lists say, and for nothing else) gets `<snapshot>=<note>` per item and returns one note each; core lands them, under the vault lock and all or none: a `wiki/` note per item (the one it has, else `wiki/notes/<title slug>.md`) with `type: import`, its project, `url`, and `snapshot`, holding exactly the `<!-- keep -->` blocks it had whatever the agent returned (`restoreKept`), a new note's `index.md` line, and a link from the Project hub's `## Imported` keep block. A locked note is left as it is. A run that fails, or whose output does not land, leaves the snapshots, changes no note, and says why (`notes.ok: false` and its `reason`; the command exits 1). Each import keeps one `vault-change` receipt listing each item with its snapshot and note. `mesa import list --project <p>` lists the project's items from the snapshots' frontmatter (the latest fetch of each, and its note), and `mesa import refresh --project <p> [<id>...] [--no-notes]` imports them again from their URLs. `mesa open <project> --from <item> [--goal <text>] [--no-notes]` starts a session from one: `<item>` is its id, or a link (or key) that resolves to it, and a link not imported yet is imported first (with `--no-notes`, without notes), while one that cannot be imported starts nothing and says why. Its goal (`sources/item-goal.ts`) names the item's title (clipped to 200 characters), its URL, and the vault paths of its note and latest snapshot, for the agent to read with `mesa-vault`'s `read_note`, then the `--goal` text; `--exact-goal` makes `--goal` the whole goal instead, and `--goal-file` is refused. A Write notes run that fails in that first import is a `warning`, and the session starts all the same. The record keeps the item as `from: {source, id}`. `mesa import goal <item> --project <p>` prints that goal without starting; Start session on an item of the Context tab, or on the one item ticked in the Picker (imported first), switches to the Overview with the project's goal box filled in with it, to edit, and the session it starts keeps the item. The vault frontmatter is the only record: nothing goes in `mesa.yaml` or the profile. A new Source adds a row to `CONNECTORS` (`sources/connectors.ts`: its connection and its fetch) and its links to `links.ts`.
Not: sync, clip, ingest.

## Picker

Browsing a Source as a tree to tick the items to import: `mesa sources browse <source> [<node>] [--cursor <c>] [--search <q>] [--descendants] --json` prints `{node, children: [{id, kind, title, url, hasChildren, importable}], cursor?}`, or, from a connected Source's Browse on the Context tab, a dialog whose tree opens a node at a time, with Load more, a search box, the count ticked, Write notes, and Import, which is the Import of the ticked items' URLs, or, with one ticked, Start session, which imports it and starts from it (see Import). Node ids and cursors are opaque strings the Source's tree makes (`tree` in its `SOURCES` row, a `SourceTree`; Atlassian's ids are in `sources/atlassian-nodes.ts`, Notion's in `sources/notion-tree.ts`); the root, no node, lists the connection's sites (Notion's workspace). The Source's tree says which children an import takes (`importable`: Atlassian's pages and issues, Notion's pages and database rows), whose `url` is the canonical link it takes; a container's is its web page. A search looks under the node (Notion's, across its whole workspace). Ticking a page with pages under it asks whether to tick them too, every one under it up to 200 (`--descendants`). With Write notes on, more than 50 ticked disables Import and says why. A Connection that needs reconnecting shows Reconnect in the tree.
Not: Vault browser, explorer, finder.

## Automation

An optional named rule in the Profile's `automations.yaml`, never in a project's `mesa.yaml`. Each names a registered Project, an enabled toggle, `when: cron | file | state`, `run: skill | send | open | refresh`, and an explicit `guardrail: ask | allow`. Trigger details are `cron` (five numeric local-time fields), `file` (a project-relative path without `..`), or `state` (one of Faro's Agent states). Action details are `skill` and optional literal `args`, `session` and `prompt`, `goal`, or optional `notes` for Refresh. Skill, Open and Refresh may select `agent: claude | codex`; unattended notes do not default to Antigravity. Names are unique ignoring case.

`mesa automations list|add|remove|enable|disable --json` manages these rules with private, atomic, locked writes. With no file, list returns an empty array without creating one. CRUD is inert: adding or enabling never installs a scheduler, starts a session, or changes the vault. The Automations screen and each project's Automations tab offer the same rule form and toggles, with each rule as a sentence (`describeAutomation`). Execution, scheduler installation and run history are defined by the scheduler delivery (#423).
Not: workflow, task, webhook, project config.

## Release

A published Mesa version, `vX.Y.Z` (stable) or `vX.Y.Z-beta.N` (a prerelease on the beta channel), with one version for the app, the CLI and core (`pnpm release:version`, checked by `pnpm check:version`). Its GitHub Release holds the signed, notarised DMG (`Mesa_X.Y.Z_universal.dmg`, and `Mesa_universal.dmg` under a name that never changes), the update archive (`Mesa.app.tar.gz` and its `.sig`), `latest.json` (the updater's feed; a beta also replaces the one on the prerelease `beta`), and `SHA256SUMS`. The app carries the CLI as the bundled mesa, `Contents/MacOS/mesa`: a Node single executable whose skill library unpacks to `~/.mesa/.skills/`. `docs/release.md`, ADR-0017.
Not: build, deploy, sidecar (the bundled mesa is one).

## Attribution

One third-party package a Release ships, with its version, license and license text: the Node inside the bundled mesa, an npm package bundled into the CLI or the app, a Rust crate of the app, or a vendored skill. `scripts/release/licenses.mjs` lists them, and `build.sh` embeds the file in the bundled mesa beside the version and the build number (the commit count, the app's `CFBundleVersion`). `mesa about licenses` and the app's About Mesa screen show them; a development mesa has none and its build is `dev`.
Not: credit, notice (a NOTICE file is one source of the text).

## Update channel

Which Releases Mesa updates to: `stable` reads only stable releases; `beta` reads the beta feed and stable too, and takes whichever is newer. Set per profile in `update.channel` (`mesa update channel [stable|beta]`, Settings > General); unset, it follows the running version, so a beta tracks betas. Only a version above the running one is offered, never a downgrade. A version listed in `revoked.json` on the `beta` prerelease is revoked: the app blocks with its reason until an update replaces it. ADR-0018.
Not: track, ring, branch.
