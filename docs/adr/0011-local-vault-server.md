# ADR-0011: The local vault server speaks stdio, binds by environment, and is inert outside a session

Status: accepted
Date: 2026-09-29

## Context

Every Mesa session should reach its profile's vault on demand, with a standing context cost that does not grow with the vault (#157). The spike (`docs/spikes/vault-mcp.md`, #292) showed that Claude Code 2.1.284, Codex CLI 0.157.1 and Antigravity CLI 1.2.13 all mount a hand-rolled stdio MCP server, and that each gives it the Mesa window's `MESA_SESSION_ID` and `MESA_PROFILE` (Codex through `env_vars`). It also showed two risks. Antigravity has one global entry, which every `agy` process on the machine starts, including processes outside Mesa. The global allow rule `mcp(mesa-vault/*)`, which `mesa hooks install` adds, lets any of those processes call the server without a prompt. The vault owners already existed when this server was written: the Vault scope, the reader, search, Project context and session goals, and Session writes.

## Decision

- **Transport.** `mesa vault mcp` is the `mesa-vault` server. It speaks newline-delimited JSON-RPC 2.0 on stdin and stdout, hand-rolled in `packages/core/src/lib/mcp-server.ts` with no SDK and no dependency. It has no network listener, port, or socket, and it lives as long as the agent keeps its stdin open. It answers `initialize` with the client's `protocolVersion` when it speaks that version (`2025-11-25`, `2025-06-18`, `2025-03-26` or `2024-11-05`), and with `2025-11-25` otherwise. It also answers `ping` with `{}`, `tools/list`, and `tools/call`. It never replies to a notification. It answers every other method with `-32601`: Antigravity's `server/discover` falls back to `initialize` on that error. An unknown tool gets `-32602`, and a line that does not parse gets `-32700`. It ignores params it does not know, such as Claude's `_meta`. Requests are answered one at a time, in order. Only JSON-RPC goes to stdout. Stderr gets one line saying whom the server serves, plus any internal error (`-32603`). The CLI command returns a `serve` loop, which the entrypoint runs on the process's stdio instead of printing anything (the `exec` pattern of `mesa open --attach`). This lets tests drive the same loop in memory.
- **Binding.** The binding comes from the environment only, in `vault/binding.ts`. The mount is `<mesa> vault mcp` with no `--profile`: the profile is the one `MESA_PROFILE` selects, and the session is the one `MESA_SESSION_ID` names. It is read through the Caller (`sessions/caller.ts`) and checked again on every request. The server is bound when that profile has the session and the session has no `endedAt`. Otherwise it gives one of these reasons: `MESA_SESSION_ID is not set: this is not a Mesa session`, `profile <p> has no session <id>: it is unknown or was removed` (which also covers another profile's session), `session <id> is profile <q>'s, not <p>'s` (a `--profile` against the window's `MESA_PROFILE`), or `session <id> ended at <time>`. A session stopped while its server runs is refused from its next request on.
- **Inertness.** An unbound server still completes `initialize`. It then lists no tools and answers every `tools/call`, whatever the name, with the tool error `mesa-vault is inert: <reason>`. It reads and writes nothing in the vault. This is a security requirement, not an optimisation: an `agy` process outside Mesa, or any other client without a live session, gets nothing, even with the allow rule. It also spares those processes the tool list's standing cost.
- **Scope.** The Vault scope (`vault/scope.ts`) stays the one rule. Each tool reaches the vault only through an owner that applies it, so the server's own call path refuses a canonical-path escape, an absolute path, a symlink that leaves the vault, and a vault internal, each with the owner's reason. Reads default to the session's project: `project_context` with no argument gives that project's overview, or the whole-vault overview for a General session. `search_vault` filters to that project unless it is given another `project` or `all: true`, and a General session searches the whole vault. `session_goals` lists that project's goals. Both leave the calling session out by passing it as `exclude`. `read_note` reads any item in scope. Writes are attributed to the session and its project. The session goes in the note's frontmatter and becomes the receipt's `actor` through the Caller. A note in another project's folder is refused, and a General session has no project to save a decision for. After `/clear` in Codex or Antigravity, the server keeps the window's `MESA_SESSION_ID` (ADR-0010). Writes from the cleared conversation are still that Mesa session's, in the same window and project, so they are allowed.
- **Tools.** There are seven tools, defined in `vault/tools.ts`. Each input is a strict zod schema, and its JSON Schema is derived from it, so the listed schema and the validation are the same rule. Each tool calls the owner its `mesa vault` command calls and answers with that command's `--json` data as JSON text. An owner's refusal, or arguments the schema refuses, become a tool error with the reason.

  | Tool | Owner | Command |
  | --- | --- | --- |
  | `project_context [project]` | `vault.context` (`projectContext`) | `mesa vault context` |
  | `read_note path` | `vault.read` (`readVaultItem`) | `mesa vault read` |
  | `search_vault query [project] [all] [limit, 1 to 50]` | `vault.search` (`searchVault`) | `mesa vault search` |
  | `session_goals [limit, 1 to 20]` | `vault.goals` (`sessionGoals`) | `mesa vault goals` |
  | `save_decision title decision rationale [probabilities] [confidence]` | `vault.saveDecision` | `mesa vault save decision` |
  | `save_summary summary` | `vault.saveSummary` | `mesa vault save summary` |
  | `save_note title body [path]` | `vault.saveNote` | `mesa vault save note` |

- **Recording.** The server records nothing of its own: starting, listing, and refusing create no receipt. Reads create no receipt. A save records exactly as its Session write does: one receipt and one log line for a substantive change, and nothing for a repeat (#274).
- **Size.** The definitions are fixed. The `tools/list` result, `{"tools":[...]}` as compact JSON, is **2,590 bytes** whatever the vault holds. As a JSON-RPC line with its id it is 2,624 bytes. `mesa vault mcp --tools --json` prints the same list without serving, for the app's Session details and for this record. `packages/cli/src/commands/vault.test.ts` asserts the size, so a change to a description or schema must update this ADR.

## Evidence

- The spike's clients and their sequences (`docs/spikes/vault-mcp.md`). Its throwaway list of seven tools was 2,439 bytes for the tools array, and it cost 854 tokens in Claude Code with tool search off and about 850 tokens in Antigravity. With tool search on, Claude Code defers MCP tools, and Codex always does, so the standing cost there was 0 tokens. This list is 151 bytes longer, from real input schemas (`probabilities`, `all`, `limit` bounds).
- `packages/cli/src/commands/vault.test.ts` drives `mesa vault mcp` through the CLI harness over in-memory stdio, with an invented vault and invented session records. It covers `server/discover`, `initialize`, the notifications, `tools/list`, a call to each tool, `ping`, an unknown tool, an unknown method, and a line that does not parse. It checks version negotiation, the six inert cases, a session stopped mid-run, the scope refusals and bad arguments through the call path, a General session, and `--tools`. Every stdout line is checked to be JSON-RPC 2.0.
- The built CLI was run over a real pipe with a throwaway profile, an invented vault, and an invented session record. `MESA_SESSION_ID=<id> MESA_PROFILE=<profile> node packages/cli/dist/mesa.js vault mcp < requests.jsonl` exited 0 when its input ended. It wrote five JSON-RPC lines to stdout (`-32601` for `server/discover`, `initialize`, seven tools, the project's overview, and `{}` for `ping`) and `mesa-vault: serving session <id> (<project>)` to stderr. Without `MESA_SESSION_ID`, it listed `[]` and refused `save_note` with the inert reason.

## Consequences

- The launch mount (#301) is `<mesa> vault mcp` with no profile flag. Claude Code and Codex repeat it on every resume, and Antigravity's single global entry is enough.
- The binding trusts the process environment. A local process that sets a live session's `MESA_SESSION_ID` gets that session's vault access. This is the same trust as the `mesa` CLI itself, which the same user can run directly, so it is not a boundary against the local user.
- Antigravity caches each server's tool schemas per server name in `~/.gemini/antigravity-cli/mcp/<name>/`, shared by every `agy` process. An outside process that gets the inert empty list may rewrite that cache while a Mesa window relies on the full list. The spike did not observe this, and the final qualification (#302) checks it.
- A session record that does not read makes `tools/list` and `tools/call` internal errors, which are logged to stderr. It never yields tools.
- Answers are the commands' JSON, so a call costs its result's size, and each owner bounds that size (the overview at 8,000 bytes, search at 50 items, goals at 20).
