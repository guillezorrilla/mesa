# ADR-0027: The phone app is Expo in the monorepo, released by EAS, updated over the air

Status: accepted
Date: 2026-11-11

## Context

Epic #902 pairs an iPhone with Mesa so a person is pinged when a session needs them, reads what it said, replies, and answers its prompts away from the desk. The owner chose a native app over a home-screen web app or a Telegram bot (2026-11-10, docs/spikes/orca-comparison.md, Mobile) and left SwiftUI or Expo open. On 2026-11-11 the owner added requirements: updates over the air, CI/CD that releases with no hand steps, an efficient app, and clean code. orca's mobile app was read as a candidate to reuse. The stack, the repo, the release path and the identifiers are hard to change once a build is on the phone, so they are recorded here. What the broker carries for the phone is ADR-0014's amendment.

## Decision

**Expo, not SwiftUI.** Only Expo's `expo-updates` ships a change to an installed app without a new build; Apple allows no native code over the air, so SwiftUI would make every change a TestFlight build. Expo also shares TypeScript, Biome, vitest and the mailbox and crypto types with `packages/core` and `apps/broker`. The app is React Native on the New Architecture with Hermes and `expo-router`, on the newest stable Expo SDK and the React and React Native it pins when the app is created, and on each SDK after. Text is rendered natively; no WebView and no terminal emulator, which are the heavy part of orca's app.

**React 19 as written.** The React Compiler is on, so no hand-written `useMemo`, `useCallback` or `memo`. Data is read with `use()` under `Suspense` and error boundaries, not effects that fetch into state; a reply or an answer is a form action with `useActionState`, shown at once with `useOptimistic`; `ref` is a prop (no `forwardRef`) and a context is its own provider. An effect is only for a subscription to something outside React, such as the mailbox socket, with `useEffectEvent` for its callbacks.

**A design system with one component library.** The app's look is Mesa's: `apps/mobile/src/global.css` holds the same tokens as `apps/desktop/src/style.css` (oklch colors for light and dark, the radius, IBM Plex Sans and Mono), as Tailwind v4 theme variables for Uniwind, which compiles Tailwind classes to React Native styles at build time rather than at render. Uniwind cannot read the desktop's `[data-theme]` selectors, so the file is a copy, and a test fails when a token's value differs from the desktop's. Every screen is built from `apps/mobile/src/components/`: `ui/` holds the domain-free primitives (Text, Button, Card, Badge, Input, Sheet, Dialog and the like) taken as source from `react-native-reusables` (shadcn/ui's port, its Uniwind variant) and owned here like the desktop's shadcn components; the rest are Mesa's own composites (a session row, a state dot, an agent mark, a prompt card), each in one file, built only from `ui/` and the tokens, with `lucide-react-native` icons, each imported by its path (`lucide-react-native/icons/<name>`): the package root bundles every icon, which made the first bundle 7.5 MB against 5.1 MB, and Biome refuses it in `apps/mobile`, as it refuses `useMemo`, `useCallback`, `memo` and `forwardRef`. IBM Plex is embedded by the `expo-font` plugin, so no font loads at start and iOS picks each weight from the family. Every component has one job and stays small: a screen composes components and one hook, a hook owns one piece of state or one subscription, text and formatting live in pure functions with their own tests, and a component that needs "and" to describe it is split (owner, 2026-11-11). orca's components are styled with React Native's `StyleSheet` and tied to its own screens, so none is taken whole; its state dot, agent marks and pairing scanner's reticle are worth reading before Mesa's are drawn.

**orca's app is read, not forked.** It is MIT, Expo 55 and React Native 0.83, about 3,000 source files, released by fastlane, with no `expo-updates`. Most of it serves orca's own RPC protocol, its relay director, its accounts, a WebView terminal, dictation and Android. Ideas taken from it: a QR that carries the endpoint, a token and a public key; the APNs environment (`aps-environment`) set to production rather than left at Expo's development default, without which TestFlight pushes are lost (Mesa sets it for every build, so the native fingerprint CI computes is the build's own); an iOS release separate from the desktop's. A file copied from it keeps its MIT notice.

**In this repo, as `apps/mobile`.** One PR can change the broker, core, the CLI and the phone together, as AGENTS.md asks, and the mailbox and crypto types have one owner in core. `apps/mobile` is a pnpm workspace package like `apps/desktop`. It keeps its own version: `scripts/release/version.sh` and `pnpm check:version` skip it, because the desktop releases weekly and a phone build follows only native changes.

**Identifiers.** Apple team `EMTB6K854Q`, following the owner's other app. The app is `com.guillezorrilla.mesa`, with Push Notifications and App Groups; the Notification Service Extension is `com.guillezorrilla.mesa.notifications`; the two share a Keychain access group, through which the extension reads the pairing key, and the app group `group.com.guillezorrilla.mesa`, registered for a shared container should one be needed. The App Store Connect record is "Mesa: Agent Sessions" (`ascAppId` 6833602462; the plain name was taken); the name under the icon is `Mesa`.

**The one native part.** The extension decrypts a push before it is shown. It is Swift, kept in `apps/mobile/targets/notifications/` and added to the generated Xcode project by a config plugin in `apps/mobile/plugins/`, so `ios/` is never committed (Continuous Native Generation). An over-the-air update never changes it.

**Crypto that every side has built in.** X25519 to agree a key, HKDF-SHA256 to derive one key per direction, ChaCha20-Poly1305 to seal each message with a random nonce. The pairing protocol (the message schemas, the key derivation, seal and open) is one TypeScript module in core with no Node imports, on `@noble/curves` and `@noble/ciphers` (audited, pure TypeScript), which the Mac, the broker's tests and the app all import; the app takes it from `@mesa/core/phone`, an entry holding the protocol alone, so nothing else of core is bundled; the extension's CryptoKit code is the only second implementation, and both check the same fixed test vectors. orca's NaCl boxes would need libsodium in the extension.

**Release.** EAS Build makes the iOS build in Expo's cloud and EAS Submit uploads it to TestFlight with the App Store Connect API key; EAS Update serves updates over the air. `runtimeVersion` uses the `fingerprint` policy, so an update reaches only builds with the same native code. EAS keeps the build number (`cli.appVersionSource: remote`, `autoIncrement`), so CI commits nothing to `main`; the marketing version in `app.config.ts` changes by hand in a PR. Credentials live in EAS (the ASC API key, the distribution certificate, the profiles); GitHub holds none.

**CI.** `pnpm verify` covers `apps/mobile` like any package: Biome, typecheck and vitest over its logic, plus `expo-doctor`. Releases run on EAS Workflows (`apps/mobile/.eas/workflows/`), Expo's own CI, rather than GitHub Actions calling `eas`: Expo documents it for this flow, and its `fingerprint` job runs where the build does. A fingerprint computed on a GitHub runner differed from the builder's (the runner resolved the `web` platform, the builder did not; 2026-11-12, build fb443e59), and an update is only offered to builds whose runtime version matches, so the app also names its one platform (`platforms: ['ios']`). `deploy-to-production.yml` is Expo's "Deploy to production" example for iOS: on a push to `main` touching the app, `fingerprint`, then `get-build` by that fingerprint, then either `update` to the `production` branch or `build` and `submit` to TestFlight. `pull-request.yml` runs the same fingerprint and lookup and shows a check when a merge would need a build. The workflows are triggered by the Expo GitHub app linked to the project (base directory `apps/mobile`); GitHub holds no Expo token. TestFlight's internal group goes to the owner's phone; App Store release is out of scope.

**The request layer (#1017).** The phone asks and the Mac answers over the Pairing's mailbox, in `packages/core/src/phone/protocol/`, which both sides import. `rpc.ts` holds the zod schemas: a `request` names a `call` (`sessions`, `session` with an id, `mark` read or unread) and an id; the `response` carries that id with the call's result or an error, and the side that asked checks the result against `callResults`; an `update` is what the Mac pushes on its own: the rows that changed, the ids gone, and the whole attention order, so a row that moved keeps its rank on the phone. A call is answered by the same core functions the CLI uses (`sessions`, `review responses`, `logs --tail`, `read`, `unread`), through `phone/serve/answer.ts`. The list travels as slim rows (id, title, project, state, since, context %, unread; about 200 bytes against `mesa sessions --json`'s 2.3 KB). A message whose JSON is over 6,000 bytes, which with the envelope is what seals under the broker's 8,192-character box, is cut by `chunk.ts` into numbered parts of 4,096 bytes sent base64url, each a sealed box with its own seq, so a replayed or reordered part is refused like any box; the receiver puts them back together and drops a payload still missing a part after 8 s (checked on its next frame in or message out), failing the call it answered as lost; a payload is at most 150 parts (600 KB), inside the 200 boxes the broker keeps for a side. `mailbox.ts` is one side's end over the broker's WebSocket (auth, open, reassemble, ack, seal); `requests.ts` the phone's calls, each failing after 10 s, which is how the app knows the Mac is asleep. Seqs rise with the clock (microseconds, above the last), so neither side writes its sent seq on every box; each keeps its last taken seq, the Mac in its Keychain item and the phone in its own. A new call is a new member of `phoneCall` with its result schema and a branch in `answerCall`, and nothing else. A family of calls may keep its schemas in its own protocol file and answer through one branch that hands it to its own module, as the crew's do (`protocol/crew.ts`, `serve/crew.ts`, #1066), so `rpc.ts` and `answer.ts` stay small. #1018 added `prompt` (a session's Pending prompt, through `sessions.prompt`) and `answer` (through `sessions.answer` with `via` `phone`, always naming the prompt's id; a stale answer is a result, `{status: 'stale'}`, not an error), and an optional `ask` on the slim row: a waiting session's prompt in one line, read on each board look, so Needs you says what each session asks.

**A large diff travels a page at a time (#1063).** The calls for reviewing a session's changes, its source control and its files are in `protocol/changes.ts`, answered by `serve/changes.ts` through the same core functions as `mesa diff`, `review notes`, `review send`, `git` and `files`. The `changes` call sends only the changed files with their counts (about 80 bytes a file); a file's diff comes in pages of its patch lines (`diff` with `from` and the file's revision, so a page of a patch that changed since the first is refused rather than skipping or repeating lines), at most 400 lines or 48 KB, a longer line cut at 2,000 characters, each page carrying the old and new line numbers where it starts (`git/diff-lines.ts`, the one reader of a patch's lines, which `diffRows` and both sides use), so the phone numbers and colours a page alone and renders it in a virtualised list. A 1.37 MB diff of one file (20,000 lines) is 51 pages; measured on 2026-11-12 against `wrangler dev` with a Node phone on the real socket: the file list in 958 ms, the first page in 232 ms, all 51 in 3.2 s, the slowest page 373 ms, and 0.2 ms to read a page's lines on the phone. Reading the session's whole diff again for each page took 2 to 30 s a page on that busy Mac, so the listener keeps a session's last diff read for a minute (`serve/kept-diffs.ts`); the file list, and a pull to refresh it, always read anew. A note on lines is kept and sent alone (`review notes add`, then `review notes send --note`, without repeating the notes still open; one the guardrail stops is not kept) rather than through `review change-send`, whose hunks exist only for uncommitted edits, while the phone shows the Session diff against the base, committed or not, as the desktop's diff panel does. Discarding and force-pushing are not offered on the phone.

**The Mac's listener is a LaunchAgent the pairing installs.** `mesa phone serve` (core `phone/serve/listen.ts`) holds the socket, answers each request, and while a phone watches (a `sessions` request in the last two minutes, which the app renews every minute in front) looks at the board every 2 s and sends the rows that changed, so a state change reaches the phone within 5 s. It must answer with the app closed, so neither the desktop app nor the scheduler owns it: the scheduler is a job every 30 s (ADR-0016), too slow for a 10 s answer and with no socket between ticks, and the app is often closed. Confirming a pairing (`mesa phone status`, which the app's Phone setting runs) installs `com.mesa.phone.<profile>`, a LaunchAgent kept alive by launchd (`KeepAlive` unless it exits cleanly) and written by the same `lib/launch-agent.ts` as the scheduler's; `mesa phone unpair` removes it. With the app open or closed only that one process runs, and a lock file (`phone-listener.lock` in the profile) refuses a second `mesa phone serve` for the profile. The listener ends cleanly when the broker no longer holds the pairing (the phone unpaired), forgetting it here too, so launchd does not restart it. An idle socket costs nothing on the broker (hibernation); the listener dials again at once when a tick comes over 30 s late (the Mac slept) and every 5 minutes otherwise, since a socket can die with no close, and a phone's call left while it was down waits in the mailbox for the next dial.

**The Inbox, usage and push settings (#1067).** Three call families answer through the CLI's functions: `inbox` (the latest 50 notices, each with the session or decision gate it opens) and `noticeRead`; `usage` (`mesa usage`'s report cut to today, 7 days, the month, the last 14 days and each board session's cost beside its context, with the reached cost alerts); `pushes`, which reads `phone.push`, `phone.awayAfter` and `phone.finished` and sets them as `mesa config set` does. A notice the phone has no screen for (Doctor, a failed automation run, What's new) shows in the list and opens nothing. Automations stay on the Mac: the owner does not want them on the phone (2026-11-12). iOS shows at most five tabs before folding the rest into More, so Usage is a screen on the Mac tab rather than a tab of its own.

**No account.** The pairing is the authentication (ADR-0014's amendment). The app keeps the pairing key in the Keychain and nothing else of the person's.

## Evidence

- orca's mobile app, read 2026-11-11 at github.com/stablyai/orca: `mobile/package.json` (Expo 55, React Native 0.83, `tweetnacl`, `react-native-libsodium`, `react-native-webview`, `@xterm/xterm`, no `expo-updates`), `mobile/app.config.js` (the `aps-environment` note), `.github/workflows/mobile-ios-release.yml` (fastlane on an Xcode runner, about 30 to 40 minutes per release), 3,053 files under `mobile/src` and `mobile/app`.
- `expo/expo-github-action`'s `continuous-deploy-fingerprint` README, read 2026-11-11: it checks the fingerprint, looks for an EAS build with it, builds when there is none, and otherwise publishes an EAS Update; `auto-submit-builds` adds `--auto-submit`.
- The owner set up the app identifiers, the app group, the APNs key, the App Store Connect record and an App Store Connect API key (App Manager) on 2026-11-11. The key files stay with the owner; neither is in this repo.

## Consequences

- A JavaScript change reaches the phone minutes after merge with no TestFlight build; a change to a native module, the extension or the Expo SDK makes a build, which EAS's free plan bounds by monthly build count.
- Mesa depends on Expo's hosting for builds and updates. Leaving it means fastlane builds on GitHub's macOS runners and a self-hosted `expo-updates` server; the app's code would not change.
- The extension is the one Swift file to maintain, and changes to it ship only in a build.
