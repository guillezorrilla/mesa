# ADR-0014: Sources sign in through a Mesa-hosted OAuth broker; tokens live in the Keychain

Status: accepted
Date: 2026-10-01

## Context

Epic #166 connects a project's vault to Atlassian (Jira and Confluence) and Notion, with ClickUp deferred (added 2026-10-11, #402; Linear and GitHub added the same day, #748), and asks that anyone who installs Mesa connect in one click, with no setup guide and no pasted personal token. Each vendor's standard OAuth needs a client secret at the token exchange: Atlassian OAuth 2.0 (3LO), Notion public integrations, and ClickUp OAuth all do. Atlassian has no secretless PKCE flow for 3LO apps ([OAUTH20-2491](https://jira.atlassian.com/browse/OAUTH20-2491)). A secret shipped inside a desktop app is not secret, so something Mesa hosts has to hold it. This reverses the epic's earlier rule of "no Mesa-hosted relay", and drops MCP as the connection route: the REST APIs give a real tree with pagination and use no Rovo credits. Where the tokens live, and what the hosted part may see, are hard to change once people have connected, so they are recorded here.

## Decision

- **The broker** is a Cloudflare Worker, `apps/broker` (`@mesa/broker`, `wrangler deploy`), with no framework. Its one table, `providers.ts`, holds per source the authorize URL, the token URL, the scopes, the vendor's extra authorize parameters, and how the token request carries the client secret (in its JSON body, or as HTTP Basic for Notion) and how its body is encoded (JSON, or a form for Linear and GitHub); Atlassian, Notion, ClickUp, Linear, and GitHub are its rows. Each source's client id and secret are Worker secrets (`ATLASSIAN_CLIENT_ID`, `ATLASSIAN_CLIENT_SECRET`, `NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET`, `CLICKUP_CLIENT_ID`, `CLICKUP_CLIENT_SECRET`, `LINEAR_CLIENT_ID`, `LINEAR_CLIENT_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, set with `wrangler secret put`). Mesa's hosted one is `https://mesa-broker.guillecoto94.workers.dev`.
- **Routes.** `GET /authorize/<source>?state=S` redirects to the vendor's sign-in with the client id, the scopes, `redirect_uri=<broker>/callback/<source>`, and `state`. `GET /callback/<source>` is the only redirect URI registered with each vendor: `state` has the form `<nonce>.<port>`, the port must be 1024 to 65535, and the broker redirects to `http://127.0.0.1:<port>/callback` with the same query (the code or the error, and the state). So no vendor needs a loopback callback registered. `POST /token/<source>` takes `{grant_type: "authorization_code", code}` or `{grant_type: "refresh_token", refresh_token}`, adds the client id and secret (in the body, or as HTTP Basic where the row says so) and the same `redirect_uri` for a code, and returns the vendor's status and JSON body unchanged. An unknown source is 404, a missing id or secret 500 `not_configured`, a bad body 400. `GET /privacy` and `GET /terms` serve the privacy policy and terms the vendors' app listings link to (`https://mesa-broker.guillecoto94.workers.dev/privacy` and `/terms`).
- **What the broker sees:** the authorization code, the refresh token Mesa sends to refresh, and the access and refresh tokens in the vendor's answer, which it passes straight back. **What it never sees:** source content, and Mesa's API calls, which go from the Mac to the vendor directly. It stores nothing and never logs a request or response body (it has no logging at all).
- **The flow** (`packages/core/src/sources/connect.ts`): Mesa starts a loopback listener on 127.0.0.1 (a free port, five minutes to sign in), opens `<broker>/authorize/<source>?state=<nonce>.<port>` in the default browser, waits for the relayed callback, and checks the state is the one it sent; a mismatch, a refused consent, or a missing code stores nothing. It then exchanges the code through the broker and reads the sites the token reaches (Atlassian's `accessible-resources`; for Notion, the one workspace its bot is in, from `/v1/users/me`; for ClickUp, the Workspaces the person picked, from `/api/v2/team`; for Linear, the one workspace picked at sign-in, from the GraphQL `organization`; for GitHub, the signed-in account, from `/user`, as the repos it reads are those Mesa's GitHub App is installed on, read live each time). A source that gives no refresh token is stored without one, unless its access token expires, which then fails the sign-in.
- **Tokens live in the macOS Keychain**, one generic-password item per source under service `mesa.<profile>.sources`, account `<source>`: the access and refresh tokens, their expiry (none for Notion or ClickUp, whose tokens name no lifetime; ClickUp's come with no refresh token either), the sites (id, name, URL; Notion's workspace id and name), and a status (`connected` or `needs-reconnect`). Mesa stores no personal data from the source account (Notion's token answer names the person who signed in, its `owner`, which Mesa drops): `mesa sources list` reads the account (Atlassian's `/me`; Notion's `/v1/users/me`, the bot named after the person who added it) live with the stored token, and leaves it out when that read fails. The item is written by `osascript` (JavaScript for Automation calling `SecItemAdd`) with the value on stdin, and read and deleted with `/usr/bin/security`, so the token never appears in argv. Both are Apple's tools, so either reads the other's item without a prompt. Tokens never reach `config.yaml`, the vault, receipts, or logs.
- **One authorized fetch** (`sources/authorized-fetch.ts`) makes every call to a source's API: it adds the Bearer token, refreshes through the broker when the token is within a minute of expiry or the vendor answers 401, and stores the rotated refresh token (Atlassian, Notion, Linear, and GitHub all rotate them). A token with no expiry (Notion's) refreshes only on a 401; one with no refresh token (ClickUp's) marks the connection `needs-reconnect` on a 401, except ClickUp's 401 `Team not authorized`, which only means the item is in a Workspace the person did not pick. A rate limit with no `Retry-After` but ClickUp's `X-RateLimit-Reset` (seconds) or Linear's `X-RateLimit-Requests-Reset` (milliseconds) waits until that time; Linear's GraphQL answers a rate limit as a 400 whose error code is `RATELIMITED`, which counts as one. A refused refresh (`invalid_grant`, the `unauthorized_client` Atlassian answers once the person revoked the app, or GitHub's `bad_refresh_token`, which GitHub answers with HTTP 200), or a 401 after a refresh, marks the connection `needs-reconnect` and tells the person to reconnect.
- **Self-hosting:** deploy `apps/broker` to your own Cloudflare account (`pnpm -C apps/broker deploy`), register your own vendor apps with the callback `https://<your worker>/callback/<source>`, set their secrets with `wrangler secret put`, and set `MESA_BROKER_URL` to the Worker's URL in Mesa's environment.
- `mesa sources connect`, `list`, and `disconnect`, and Settings > Connections, are the callers. Connect and disconnect leave a `connection` receipt naming the source and its sites.

## Token lifetimes

- **Atlassian:** access tokens last an hour (`expires_in: 3600`); every refresh returns a new refresh token, and the old one stops working.
- **Notion** (Notion-Version `2026-03-11`, [Authorization guide](https://developers.notion.com/docs/authorization), [Refresh a token](https://developers.notion.com/reference/refresh-a-token)): the token answer has `access_token`, `refresh_token`, `bot_id`, `workspace_id`, `workspace_name`, `workspace_icon`, `owner`, and `duplicated_template_id`, and no `expires_in`: Notion documents no lifetime for the access token. "Refreshing an access token will generate a new access token and a new refresh token", so refresh tokens rotate. Refresh is `POST /v1/oauth/token` with HTTP Basic `client_id:client_secret` and `{grant_type: "refresh_token", refresh_token}`; the reference lists 400 `invalid_grant` and `unauthorized_client` among its errors, both of which Mesa reads as needs-reconnect. So Mesa stores no expiry for Notion and refreshes only when Notion answers 401. What a real revocation answers is checked live (docs/sources/notion.md).
- **ClickUp** ([Authentication](https://developer.clickup.com/docs/authentication), [Get Access Token](https://developer.clickup.com/reference/getaccesstoken)): the token answer is `{access_token}` alone, with no `refresh_token` and no `expires_in`, and ClickUp says "The access token currently does not expire. This is subject to change." There is no refresh grant. So Mesa stores no expiry and no refresh token for ClickUp, never refreshes, and asks to reconnect when a call answers 401 (other than `Team not authorized`). The live run (docs/sources/clickup.md) saw the same answer.
- **Linear** ([OAuth 2.0 authentication](https://linear.app/developers/oauth-2-0-authentication), read 2026-10-11): authorize at `https://linear.app/oauth/authorize` with a comma-separated `scope` (Mesa asks for `read,write`: `write` is the narrowest scope that allows the `issueUpdate` behind Assign to me, added 2026-10-11 for the Linear tracker, #748; a connection made with `read` alone reconnects once to assign) and `prompt=consent`, which shows the workspace picker again on a reconnect; the token request goes to `https://api.linear.app/oauth/token` as `application/x-www-form-urlencoded`, the client id and secret in the body. The answer has `access_token`, `token_type`, `expires_in` (86399: "valid for 24 hours"), `scope`, and `refresh_token`. Refresh is `grant_type=refresh_token` with the client id and secret (in the body or as HTTP Basic), and "the response includes a new access token and a new refresh token", so refresh tokens rotate; if the new one is lost, the same request may be replayed for 30 minutes. Linear moved every app to refresh tokens on April 1, 2026. So Mesa stores the expiry and refreshes a minute before it, about once a day of use. Linear also supports PKCE, with which the client secret is optional at the token exchange and the refresh, so a public client could sign in with no broker; Mesa keeps the broker route all the same, for one sign-in flow and one callback per source (the loopback port changes each sign-in, and the broker is the redirect URI Linear sees). An invalid token answers HTTP 401 `AUTHENTICATION_ERROR` (seen 2026-10-11 against `https://api.linear.app/graphql`), which the authorized fetch treats as any 401. Not yet run live (docs/sources/linear.md): the Linear app is not registered.
- **GitHub** ([Generating a user access token for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens), read 2026-10-11): a GitHub App, Mesa for Tickets (`mesa-for-tickets`), with Issues read and write and the mandatory Metadata read, and "Expire user authorization tokens" on. Authorize at `https://github.com/login/oauth/authorize` with no scope (a GitHub App's permissions are set on the app); the token request goes to `https://github.com/login/oauth/access_token` as a form, with `accept: application/json`. The answer has `access_token` (`ghu_`), `expires_in` (always 28800, 8 hours), `refresh_token` (`ghr_`), `refresh_token_expires_in` (15897600, 6 months), `scope` (empty), and `token_type`. Refresh is `grant_type=refresh_token` with the client id and secret; "once you use a refresh token, that refresh token and the old user access token will no longer work", so refresh tokens rotate. GitHub answers a bad code or refresh token with HTTP 200 and `{error: "bad_verification_code"}` or `{error: "bad_refresh_token"}`, which Mesa reads as a refused grant (sign in again). So Mesa stores the expiry and refreshes a minute before it, about every 8 hours of use; after 6 months unused the refresh token expires and the person reconnects. A token reaches only the repos the app is installed on (per org or account, all repos or picked ones), so Mesa sends a person whose sign-in reaches no repo to the app's installation page, `https://github.com/apps/mesa-for-tickets/installations/new`, and reads the reachable repos live (`GET /user/installations`, then `GET /user/installations/{id}/repositories`). Not yet run live (docs/sources/github.md): the app's client id and secret are not set in the broker yet.

## Limits

Cloudflare Workers' free plan allows 100,000 requests a day and 10 ms of CPU per request. One sign-in is three broker requests (authorize, callback, token), and a refresh one, roughly once an hour of use per person for Atlassian (its access tokens last an hour), for Notion only when a token stops working, never for ClickUp, about once a day for Linear, and about every 8 hours of use for GitHub, so the free plan serves thousands of people a day. Past it, requests fail until the daily reset, and a paid plan lifts the limit.

## Evidence

Live run, 2026-10-02, broker deployed at `https://mesa-broker.guillecoto94.workers.dev` on the Cloudflare free plan, throwaway profile `p8-live`, a company Atlassian site reached from an OAuth 2.0 (3LO) app registered under a personal developer account with sharing on:

- The first two consents stopped on Atlassian's "Something went wrong" page; its "Information for the owner" named the scopes requested but not added to the app (first the three granular Confluence scopes, then `read:hierarchical-content:confluence`). Once they were added, `mesa sources connect atlassian` opened the consent screen, and one Accept returned through `/callback/atlassian` to the loopback listener: `connected`, the company site, and a `connection` receipt naming only the source and site.
- `accessible-resources` answered two rows for the one site (one per product, same id, Jira and Confluence scopes), so sites are de-duplicated by id.
- The token read a Confluence page (`body-format=view`), its direct children, the spaces, a Jira issue with `renderedFields`, and its comments, all 200. The ancestors endpoint answered 401 "scope does not match": the granted Confluence scopes were `read:page:confluence read:space:confluence search:confluence`, without `read:hierarchical-content:confluence`, so ancestors are built from each page's `parentId`.
- `security find-generic-password -s mesa.p8-live.sources -a atlassian` found the item; it held no name, email, or account id. `grep -r` of `~/.mesa/p8-live` and the vault for fragments of the access and refresh tokens found nothing.
- After the app was removed at id.atlassian.com, the access token got 401 and the broker's refresh answered 403 `unauthorized_client` ("refresh_token is invalid"), not `invalid_grant`; `mesa sources list --json` then reported `needs-reconnect`. One more Accept reconnected it. `mesa sources disconnect atlassian` removed the Keychain item, left a receipt, and `list` reported `disconnected`.

Before the live run: `apps/broker/src/broker.test.ts` covers the exchange, the refresh, an unknown source, a missing secret, the callback's port check, the authorize redirect, and the two pages; `packages/core/src/sources/sources.test.ts` runs connect, list, and disconnect against fakes and finds no token or account data in the profile, the vault, the receipts, or the runner's argv; `packages/core/src/lib/secret-store.test.ts` checks the value goes in on stdin only. During development, `security -i` was found to read lines of at most 4096 bytes (a 4040-byte value failed), and `security add-generic-password -w` reading from stdin kept only 128 bytes, which is why writes go through `osascript`; a 9000-byte value written that way read back whole with `security find-generic-password -w`.

## Consequences

- Mesa depends on a service its owner runs. If the broker is down, connecting and refreshing fail, while an unexpired access token keeps working. If it moves or stops, connections need reconnecting (to a self-hosted broker, through `MESA_BROKER_URL`).
- Anyone holding the client secret could impersonate Mesa's vendor apps, so it lives only in the Worker's secrets, never in this repository.
- A new source (ClickUp perhaps later) is a row in `providers.ts`, a row in core's `SOURCES` table (how its API names the account and the sites), and its vendor app registered with the broker's callback.
- Keychain values must be printable ASCII (`security -w` prints any other value as hex), so the connection is written as JSON with non-ASCII characters escaped.

## Amendment, 2026-10-08: Jira Software scopes (#693)

The Atlassian row also asks for `read:board-scope:jira-software`, `read:sprint:jira-software` and `read:project:jira`, for Ticket views (CONTEXT.md). Jira Software's API takes granular scopes only, and the Atlassian app already mixed classic and granular ones, so one app holds both. A connection made before the change keeps working. A board view on it gets 401 "scope does not match", which `authorizedFetch` reports as needing a reconnect without marking the whole connection needs-reconnect. Reading one board by id (`/board/<id>`) would also need `read:issue-details:jira`, so Mesa reads a board's name from the board list instead and asks for no more. Verified live on 2026-10-08 against a company site through a local broker (`wrangler dev`, with `http://localhost:8787/callback/atlassian` added as a second callback URL): the new scopes were granted, and boards, sprints and searches all answered.

## Amendment, 2026-10-08: the first write (#695)

The Atlassian row also asks for the classic `write:jira-work`, so a person can assign a ticket to themselves when starting a session from it (the owner asked for it). It is Mesa's only write to Atlassian: one assignee, to the signed-in account, with a receipt. The classic scope is chosen over the granular `write:issue:jira` because Atlassian's spec lists it as the current scope for `PUT /issue/{key}/assignee` and the granular one as Beta. A connection made before the change fails assigning alone with the reconnect error.
